## 概述与何时用

本 Skill 覆盖 AI 基础设施与部署层的攻击面：AI/ML 系统最终都跑在别人的云账户和容器编排平台上，继承了云和容器的全部固有弱点，又叠加了 ML 特有的新弱点（大范围 IAM 角色、共享 GPU 计算、模型/特征数据在多个存储和流水线间流转）。适用信号：

- 目标暴露了一个可控参数的 Web/API 端点（导出、报表生成、webhook 回调等），怀疑存在 SSRF。
- 已知目标使用云托管 ML 服务（SageMaker/Vertex AI/Azure ML）、对象存储桶、模型注册表（MLflow 等）。
- 已获得某容器/Pod 的 shell 或服务账户 token，需要判断能走多远。
- 目标 ML 训练/推理跑在 Kubernetes 上，涉及 GPU 节点。

不覆盖：模型本身的对抗样本/提示注入（见 [[attack-single-agent]]）、MCP 工具滥用（见 [[attack-mcp]]）、代码执行与模型篡改的通用手法（见 [[code-exec-and-tampering]]）。

## 在 SOP 中的位置

对应 枚举→攻击→检测→规避 中的“攻击基础设施层”：拿到初始立足点（泄露凭据、SSRF、被钓鱼的开发者会话）之后，本 Skill 负责把这个立足点转化为跨服务/跨命名空间的持久访问。与 [[recon-ai-targets]] 衔接（被动/主动侦察先摸清云服务商、K8s 发行版、部署模式），产出的凭据/访问面可以再喂回 [[attack-mcp]]、[[attack-rag-pipelines]] 等针对具体组件的攻击；跨信任区规划见 [[target-reconstruction-engagement]]。

## 方法与技法（按小节）

### 9.1 云服务配置错误

1. **明确共享责任边界**——先确定哪些是云厂商托管、哪些是客户配置的（IAM 策略、网络 ACL、存储桶策略、密钥管理）。红队价值集中在客户侧的过度授权角色、暴露端点、泄露凭据三类。
2. **通过面向用户的功能点找 SSRF，读取云元数据/环境变量**——任何接受 URL/模板/webhook 类参数的端点都值得测试 `file://`、内网地址、云元数据服务地址（如 `169.254.169.254`）。命中后优先尝试读取进程环境变量或元数据凭据端点，泄露的往往是执行角色的临时 STS/托管身份凭据。
3. **用泄露的临时凭据做身份验证再枚举权限**——拿到 access key/secret/session token 后先确认身份和角色（`get-caller-identity` 或等价 API），再系统性枚举该角色能访问的资源（存储桶列表、密钥库、其他角色的 AssumeRole 关系），而不是只满足于第一层访问。
4. **顺着 IAM 角色链做横向/提权**——ML 平台常见模式是：前端服务角色 → 数据科学家/训练角色 → 平台执行角色，每一跳权限递增。检查每个角色能否 AssumeRole 到下一个更高权限角色，托管策略（尤其是宽泛的 `s3:*`/`*Full Access` 类）经常打破项目边界，让一个项目的凭据能访问账户内所有项目的资源。
5. **系统扫描 ML 相关存储与元数据服务**——对象存储桶（训练数据、模型 artifact、实验记录、Jupyter notebook）、模型注册表（MLflow 等）、托管数据库表、跨项目的参数/密钥存储都要枚举；这些位置经常内嵌额外密钥，形成新的攻击路径入口。同时检查模型服务端点本身是否可未授权访问（暴露公网、无认证的推理 API），可导致资源滥用、模型抽取、决策逻辑逆向。
6. **版本信息驱动定向漏洞研究**——从模型元数据、健康检查响应等处收集推理框架/服务组件的精确版本号，结合部署用途和硬件画像，去匹配已公开 CVE，评估是否存在可利用的已知漏洞而非盲目尝试。

### 9.2 容器与编排利用

1. **判断部署模式与身份原语**——先确定是托管 K8s（EKS/AKS/GKE）还是自建（kubeadm/Rancher），命名空间划分和工作负载类型（Jupyter、训练批处理、推理服务、实验跟踪、监控）。识别身份三要素：ServiceAccount、Role/ClusterRole、RoleBinding/ClusterRoleBinding。
2. **拿到一个 Pod 权限后先做权限自查**——用 Pod 内挂载的 ServiceAccount token 查询 API Server，枚举自己能做什么（`can-i` 类自省）、能读哪些 Secret、命名空间拓扑。优先探测经典提权路径：能否创建/修改 Pod（能创建 Pod 基本等价于拿到整个集群的高权限，因为可以用任意 ServiceAccount 身份起 Pod 或挂载宿主文件系统）；能否跨命名空间读 Secret；有没有更高权限的 token 挂在自己能访问的地方。
3. **优先选单容器工作负载做初始侦察，再回头打多容器 Pod**——推理服务类单容器 Pod 通常权限面更清晰、风险更低，适合先摸底层身份和网络拓扑；多容器（sidecar/init）Pod 往往安全上下文更复杂，留到后面专门做 sidecar 滥用。侦察时留意配置文件/ConfigMap 中泄露的内部服务地址、对象存储桶名、实验名称等，把盲目枚举变成定向打击。
4. **识别过度授权 ServiceAccount 并跨命名空间横向**——发现某 ServiceAccount 拥有对任意命名空间任意 Pod 的 exec 权限时，用它直接进入其他命名空间的目标 Pod（如多容器推理流水线），复用已观察到的合法访问模式（如管理员已用过的命令历史）降低异常度。
5. **滥用 sidecar/init 容器的共享卷做数据面攻击**——多容器 Pod 内所有容器共享网络命名空间，通常也共享卷；检查每个容器挂载共享卷的读写权限（`readOnly: false` 的越多，攻击面越大）。拿到可写访问后可以：读取流经队列的全部推理请求（数据窃取）、在推理容器读取前篡改请求内容（例如把高优先级关键词替换为低优先级，造成误分类）、注入伪造请求探测模型行为、篡改共享日志掩盖痕迹或伪造审计条目。init 容器留下的文件（模型 artifact 之外的内容，如凭据、内部配置）也要检查。
6. **GPU 直通层的容器逃逸**——ML 工作负载常用 GPU 直通，容器运行时会把设备内存和驱动接口暴露给容器，这些接口位于内核常规隔离边界之外，构成独立的攻击面。做法：枚举容器运行时组件版本（如 NVIDIA container toolkit、runc）与配置项（如 CUDA 兼容模式的钩子设置），对照厂商安全公告匹配已知漏洞链（例如利用 runc 在生成 OCI 钩子前把容器环境变量注入自身进程环境、叠加运行时钩子未清空继承环境的缺陷，通过 `LD_PRELOAD` 等环境变量注入实现宿主机代码执行）。

### 9.3 总结与系统化方法

把 9.1/9.2 串成一条完整攻击链的方法论：从单点入口（SSRF/泄露凭据/钓鱼拿到的开发者会话）→ 身份枚举与角色/RBAC 关系图 → 沿着信任边界（IAM AssumeRole 链、跨命名空间 ServiceAccount 权限、共享卷/GPU 设备接口）逐跳升级 → 在每一跳评估“止损点”：是否已经拿到足以证明业务影响的访问（如账户级数据、跨项目穿透、可篡改的推理数据流)。系统化检查清单：过度授权的角色/RoleBinding、暴露的端点、自动挂载的 token、缺失 Pod Security Standards 的命名空间、共享卷的读写权限矩阵。

### 9.4 技战法编排：工作负载身份图与控制面差分（实战综合；非课程原文）

把云上 AI 系统画成“运行单元—身份—控制面—数据面—制品”的关系图：Pod/VM/Job 使用哪个工作负载身份，该身份能调用哪些控制面 API，API 能影响哪些对象存储、模型注册表、流水线和其他工作负载。每获得一个新执行位置，都重新采集这五类关系，不沿用前一节点的假设。

优先做控制面差分：同一个列举、读取、创建或更新动作分别从应用接口、容器内 SDK、云 API 和流水线身份执行，比较返回对象范围、字段完整度和后续工作流，定位应用语义与底层云能力之间的差异。

容器侧按层推进：运行时画像（进程、挂载、设备、sidecar、网络）→ 同 Pod 共享关系 → 节点接口与 GPU runtime → 控制面对象 → 权重、数据集、检查点和缓存的真实存储位置。每一层只验证单跳效果，再组合成链。例如“能更新模型注册表条目”与“推理服务会自动加载最新条目”是两个独立事实；必须观察加载事件和服务行为变化才能证明完整替换链。

## 验证标准

- **工具调用成功 ≠ 漏洞已验证**：SSRF payload 返回 200、`aws sts get-caller-identity` 跑通、`kubectl exec` 进了 Pod，这些只证明请求被处理，不等于已确认可利用的安全缺陷或已产生业务影响。
- 云侧最低验证标准：用泄露/借用的凭据实际读取到目标范围外的资源（跨项目桶、跨账户角色），并记录该资源确属越权范围（对照预期的 IAM 边界文档或合同约定的授权范围）。
- 容器侧最低验证标准：证明当前身份/Pod 确实能执行原本不该被允许的动作（跨命名空间读 Secret、创建任意 ServiceAccount 的 Pod、写入其他容器读取的共享卷），并有回显或副作用证据（读到的具体 Secret 内容、成功创建的 Pod 名、被篡改后确实影响下游分类结果的对比）。
- GPU/运行时逃逸类需明确版本号 + CVE 匹配 + 实际触发（宿主机侧观察到代码执行的证据，如写入宿主机文件、获得宿主 shell），仅版本匹配不算已验证。
- 所有验证必须在用户已授权的靶场/工程内进行，不得对生产/未授权系统尝试。

## 常见失败与规避

- **SSRF 载荷被 WAF/参数校验拦截**：尝试不同 scheme（`file://`、`gopher://`、内网 IP 的多种表示法）、编码变体，或利用重定向链而非直接内网地址。
- **元数据服务加了 IMDSv2/token 强制**：需要先完成额外的 PUT token 握手步骤才能读取，直接 GET 会被拒绝；确认目标云厂商的元数据保护版本再调整请求。
- **托管策略权限比预期小**：不要止步于第一个 AssumeRole 失败，系统枚举当前身份能 assume 的全部角色列表，而非只试目测最可能的一个。
- **K8s exec 命令异常告警**：优先复用已观察到的合法操作者的历史命令模式（同样的 kubectl 子命令、同样的 Pod/命名空间访问顺序），降低与基线行为的偏离度，而非使用明显不同的探测方式。
- **共享卷权限矩阵判断错误**：`readOnly` 声明可能在 Pod spec 和实际挂载点不一致，务必在容器内实测写入而非只读 YAML 描述。
- **运行时/驱动版本号收集不全**：GPU 逃逸类漏洞往往需要多个组件版本精确匹配（容器运行时 + 驱动 toolkit + 内核），漏掉一个就可能误判可利用性，需交叉核对所有相关组件版本。

## 证据与报告

- 云侧：SSRF 请求/响应原文（含时间戳）、解析出的凭据来源字段名（不写入报告明文密钥本身，只记录字段名与到期时间）、`get-caller-identity` 输出、越权访问到的资源清单（桶名、跨项目对象路径）、涉及的 IAM 角色链关系图。
- 容器侧：ServiceAccount 权限自查结果（能做什么/不能做什么的清单）、跨命名空间访问的 Pod/Secret 名称、共享卷读写权限矩阵截图或 YAML 片段、sidecar 内截获/篡改的请求样本（脱敏后）。
- GPU/运行时：容器运行时、toolkit、内核版本号,对应 CVE 编号，触发前后的宿主机侧证据（文件系统变化、进程列表）。
- 所有证据关联到具体命令/请求(可复现的调用),并标注是否需要人工二次确认业务影响。真实靶场地址、密钥、内部主机名等敏感信息不进入公开报告，仅保留在授权范围内的内部记录。
