> **超课程范围声明**：主体资料在 MCP 工具滥用、工具链攻击相关部分仅边缘涉及"多工具链式调用导致的连锁效应"，**未独立成节讲授无界消耗/经济型拒绝服务**。本 skill 是对课程之外的扩展补充，方法依据 OWASP LLM10（Unbounded Consumption）、MITRE ATLAS（Impact 战术下的 Cost Harvesting / Denial of ML Service）与 NIST AI 风险管理框架蒸馏而成，不代表课程原文覆盖此主题。

## 概述与何时用

本 skill 覆盖 LLM/Agent 系统的**无界消耗**类风险：攻击者不需要突破权限边界或窃取数据，只需诱导系统对自身或第三方资源（算力、token 配额、下游 API 调用、金钱成本）做出**不成比例的消耗**，即可造成服务降级、成本失控或事实上的拒绝服务。典型触发面：

- 支持工具调用/函数调用、可能自我调用或调用其他 agent 的系统。
- 多 agent 编排（Manager/AM/Swarm 类架构），存在 agent-to-agent 委派链路。
- RAG 检索管道，召回策略缺乏上限或去重。
- 按 token 数、调用次数或模型档位（如自动路由到高成本大模型）计费的服务。

## 在 SOP 中的位置

对应枚举→攻击→检测→规避中的"资源与成本边界探测"阶段，通常在功能性攻击面确认之后、作为独立分支介入：

1. 先用 [[recon-ai-targets]] 确认目标架构：是否有工具调用、多 agent 委派、RAG 检索、计费/配额机制。
2. 若目标暴露 MCP/工具接入层，先看 [[attack-mcp]] 的工具链式攻击部分——链式调用既是数据流攻击面，也是本 skill 关注的放大介质。
3. 若目标是多 agent 编排，衔接 [[attack-a2a-multi-agent]]：agent 间任务转发/委派协议本身就是递归风暴的载体。
4. 若目标是 RAG 系统，衔接 [[attack-rag-pipelines]]：检索召回参数是放大系数的来源之一。
5. 观测到的成本/资源证据交给 [[target-reconstruction-engagement]] 纳入交战影响面评估。

## 方法与技法（按方向，非课程小节，均为扩展蒸馏）

- **上下文放大（context amplification）**：构造要求模型"完整复述/展开/逐字引用"大段上游内容（工具输出、历史消息、检索文档）的请求，观察响应体积相对输入的放大倍数；若系统对工具结果或 RAG 文档不做长度裁剪，单次调用即可把小输入放大成远超预期的输出 token 消耗。依据：OWASP LLM10（Unbounded Consumption - 无界扩展）。
- **递归/自触发工具调用**：识别是否存在"工具 A 的输出被解释为触发工具 A（或工具 B 再调用 A）的条件"的链路（如自动化任务系统里"处理完成后创建新任务"的模式）。构造一个满足触发条件、但结果仍满足下一次触发条件的输入，观察调用次数是否呈非线性增长而非收敛。依据：MITRE ATLAS（Impact — Denial of ML Service 相关模式）。
- **Agent 循环 / 任务风暴（agent loop & task storm）**：在多 agent 编排中，构造一个 Manager/AM 无法判定"已完成"的任务描述（模糊终止条件、循环引用的子任务依赖），观察是否触发子 agent 数量或委派轮次的无节制增长，而非被终止条件截断。
- **高成本模型强制路由**：若系统按任务复杂度/关键词自动路由到更贵的模型或更长推理链（如"思考模式"、多轮自我反思），尝试用低成本输入触发路由逻辑误判为高复杂度任务，观察是否被路由到不成比例的高成本档位。
- **RAG 召回放大**：向检索接口提交高召回、低精度的查询（宽泛关键词、无约束的模糊匹配),观察返回文档数量、总 token 量是否随查询宽泛度线性甚至超线性增长而无上限截断。衔接 [[attack-rag-pipelines]] 的检索面方法。
- **无价值数据灌入（garbage input flooding）**：提交对系统无实际语义价值、但仍会被完整摄入上下文/嵌入/索引管线的重复或高熵内容，观察系统是否对输入价值做任何过滤，还是照单全收并等比例消耗资源。
- **Cost Harvesting / Denial of AI Service 观测**：以上各方向的共同目标是让**每次交互的边际成本**（token、下游 API 调用、时延）显著偏离目标声明的正常范围，累积效应可表现为服务降级（真实用户体验时延上升）或计费异常（Cost Harvesting）。

### 技战法编排：先测放大系数，再定位放大环

先为一个正常业务请求建立基线向量 `B = {输入 token, 输出 token, 工具调用数, agent 跳数, 检索条目数, 时延}`，再一次只改变一个变量。用以下派生量判断放大来自哪里：

- **输出放大系数** `A_out = 输出 token / 输入 token`：适合识别冗长推理、重复生成和上下文回显。
- **工具放大系数** `A_tool = 实际工具调用数 / 用户请求中的显式动作数`：大于 1 且持续增长时，优先检查重试、反思、规划器和工具错误恢复环。
- **委派放大系数** `A_agent = 子任务或 A2A 消息数 / 初始任务数`：用于区分正常扇出和递归委派。
- **检索放大系数** `A_rag = 召回条目或累计上下文字节 / 查询字节`：用于定位宽泛查询、查询扩展、混合检索合并和去重失效。
- **边际增长率**：比较第 `n` 轮与第 `n-1` 轮的增量；稳定常数更像线性成本，持续变大的增量才支持队列堆积、递归或上下文滚雪球假设。

执行顺序采用五级阶梯：

1. **单次基线**：正常任务跑一次，记录完整调用图和资源向量。
2. **单轴放大**：只增加输入长度、任务条目数、检索宽度或一个失败工具，确认哪一轴会放大。
3. **终止条件探测**：让任务出现可恢复错误、空结果、重复结果或互相矛盾结果，观察 planner/retry/reflection 是否会收敛。
4. **交叉放大**：把已确认的两个放大环组合，例如查询扩展 × 多 agent 委派、工具失败重试 × 上下文回灌，判断增长是相加还是相乘。
5. **恢复观察**：停止输入后继续观察队列、任务状态和延迟是否回落；无法自行收敛的积压比单次高延迟更能说明拒绝服务风险。

每一级都要保留一组**对照请求**：语义相同但不会触发放大环的正常写法。没有对照组时，无法区分攻击输入导致的增长与目标本身的冷启动、网络抖动或模型随机性。

## 授权与安全边界（本 skill 的核心纪律）

- **仅对自有或书面授权的目标执行**：无界消耗类测试的失控后果（真实服务瘫痪、真实账单产生）比多数漏洞验证更容易造成不可逆影响，授权范围必须明确覆盖"资源/成本类测试"，而不能默认包含在通用渗透授权里。
- **必须限速与设上限**：任何重复请求/放大测试必须显式设置重复次数与请求间隔上限，不得构造无限循环或无限并发。本 skill 点名可用工具 **`consumption_probe`**（`src/tools/consumption.ts`）：它对授权目标端点发送有上限的重复请求，记录每次时延与响应体字节数，内置硬上限（`repeat` 最多 10 次、`delayMs` 最低 200ms 且不可被调用方参数突破），仅用于观测放大/循环迹象，不构成真实压垮测试。
- **避免真实伤害**：观测阶段的目的是"是否存在放大"，不是"能压垮到什么程度"。看到放大迹象后应停止扩大规模，转入报告与授权升级流程，而不是自行加大并发/次数去验证"能不能打垮"。
- 真实造成拒绝服务效果（服务不可用、目标方计费异常触发告警）超出常规观测范围，**必须获得 P4 级授权**（明确、书面、限定时间窗口的高风险测试授权）后才能执行，且执行前需与目标方约定止损与恢复机制。

## 可观察指标

- **token 数**：单次请求/响应的 token 消耗量，及其相对输入 token 的放大比例。
- **时延（latency）**：请求发出到响应完成的时间，尤其是随重复次数是否呈现非线性增长（暗示队列积压或递归深度增加）。
- **响应体增长（response size growth）**：连续请求间响应体字节数的变化趋势——`consumption_probe` 直接输出 `bytesGrowth`。
- **调用/委派次数**：工具调用次数、子 agent 委派轮次，是否在有限步内收敛到终止状态。
- **成本代理指标**：若可获取（如响应头中的用量信息、可观测的模型档位标识），记录被路由到的模型档位与对应的单位成本差异。

## 验证标准

区分两个不同层级的结论，不得混淆：

- **"观测到放大迹象"**（本 skill 常规产出）：通过 `consumption_probe` 等有上限工具观测到时延随重复次数上升、响应体积相对输入不成比例增长、或识别出理论上可递归/自触发的调用链路。这只说明**存在放大的可能性**，是否可被恶意利用致真实拒绝服务仍需人工复核。
- **"造成实际拒绝服务"**（需要 P4 授权才可执行的独立阶段）：目标服务对正常用户可观测地降级或不可用，或目标方计费系统记录到异常量级的费用。这类结论需要目标方可确认的服务状态证据（如目标自身监控/账单），且执行前必须已获得书面 P4 授权与止损约定。

工具调用成功（如 `consumption_probe` 正常返回样本数据）本身不等于以上任一结论成立——它只是采集了观测数据，结论仍需人工判读。

## 常见失败与规避

- **误把正常缓存/限流表现当作"未放大"**：目标可能对重复请求做了缓存或限流，短时间内观测不到放大不代表不存在——应变化输入内容（而非仅重复相同请求）以规避缓存命中，观察是否仍是真实的重复处理。
- **观测窗口过短漏判递归**：递归/自触发链路可能需要多轮才显现指数增长趋势，单次少量重复可能仍处于线性区间——在硬上限内尽量使用足够的重复次数和真实变化的输入去观察趋势，而非只看单次差值。
- **把工具报错误判为放大失败**：目标端点可能因参数格式、鉴权等原因返回错误而非真实处理放大请求，需先确认请求本身有效（status 正常且响应体反映了真实处理），再基于有效样本判断放大趋势。
- **混淆"高延迟"与"真实拒绝服务"**：延迟升高可能只是正常负载下的合理表现，不代表服务不可用；务必以目标方可确认的"服务降级/不可用"证据而非单纯延迟数字下结论。

## 证据与报告

- `consumption_probe` 的完整原始样本序列（每次请求的 status、latencyMs、bytes）与摘要统计（avgLatencyMs、bytesGrowth）。
- 触发放大/递归的具体输入构造（脱敏后可复现的请求模板，非目标专属凭据/路径）。
- 观测窗口内请求次数、间隔时间与对应趋势图/数据表，说明是否呈非线性增长。
- 若涉及路由到高成本模型档位，记录可观测到的档位标识差异（如响应头、返回内容中的模型标识）。
- 报告中必须明确标注：本次仅完成"观测到放大迹象"层级的验证，是否需要进一步 P4 授权测试以确认"实际拒绝服务"效应，交由目标方与授权方决定。
