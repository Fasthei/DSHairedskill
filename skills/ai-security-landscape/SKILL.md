## 概述与何时用

本 skill 覆盖主体资料 Introduction to Red Teaming AI Systems 的三节：1.1 课程概览、1.2 AI 安全格局、1.3 小结。它不提供具体攻击技法（那些在其余对应的 skill 里），而是回答两个更早的问题：

- 为什么 AI 集成系统是一类不同的安全目标，传统渗透测试思路在哪里会失效、在哪里仍然成立。
- 面对一个新目标，用什么框架组织侦察→攻击→检测→规避的全过程，以及用什么词汇向利益相关方汇报影响。

适用场景：拿到一个新的 AI 集成环境（agent、RAG、模型托管、A2A 编排、供应链）授权测试，且团队/模型还没有形成整体攻击面认知时；或者需要决定"这次任务该先看哪个章节 skill"时，先用本 skill 定位再路由。跨章节路由和总 SOP 细节见 [[ai-redteam-methodology]]（12 号 skill）。


## 在 SOP 中的位置

在「枚举→攻击→检测→规避」总流程之前的一层：定位与框架选择。

- 本 skill 产出的是"这个目标属于哪类 AI 攻击面、该用什么框架汇报、大致该去哪个后续 skill"的判断，而不是具体动作。
- 下游衔接：确定目标类型后，路由到对应章节 skill——单 agent 见 [[attack-single-agent]]、多 agent/A2A 见 [[attack-a2a-multi-agent]]、RAG 见 [[attack-rag-pipelines]]、MCP 见 [[attack-mcp]]、供应链/代码执行见 [[code-exec-and-tampering]]、云/容器见 [[cloud-and-container]]，侦察阶段统一先看 [[recon-ai-targets]]。
- 目标信息不全、需要重建架构和交战边界时，衔接 [[target-reconstruction-engagement]]（威胁建模）。

## 方法与技法（按小节）

### 1.1 课程结构与前置能力定位

- 先确认操作者已具备传统渗透测试基线能力（网络枚举、漏洞利用、持久化、规避），本 skill 及后续章节 skill 是在此基线上叠加 AI 专属攻击面，不是替代基线方法论。
- 面对新任务时，先判断目标落在哪个复杂度层级——是单模型/单 agent，还是多 agent 编排、RAG 管道、模型托管/部署管道、还是供应链——用这个层级判断去挑选该路由到哪个后续 skill，而不是一上来就套用某个具体技法。
- 报告蓝队价值：红队动作触发的遥测和日志模式本身就是防御侧的检测线索，产出报告时应同时体现"如何被检测到"，衔接 [[recon-ai-targets]] 中的检测与规避小节。

### 1.2 AI 系统为何是不同类别的目标

- **价值从文件转向行为（value moves from files to behavior）**：敏感资产不再只存在于文件/数据库里，而是存在于模型输出、决策路径和 agent 触发的动作中。评估影响面时，除了数据泄露，还要问"如果这个决策/输出被篡改，会造成什么后果"。
- **新的持久化路径**：投毒记忆、投毒 RAG 索引、投毒训练/微调数据都可以成为持久化机制，效果类似传统的后门/驻留，但落点在数据层而非二进制层。具体技法见 [[attack-single-agent]]（记忆攻击）与 [[attack-rag-pipelines]]。
- **自主行为放大攻击者能力**：agent 可以调用工具、跨系统执行动作，一次可靠的模型操纵可能级联成大规模操作性、法律、财务影响，而不只是单点数据泄露。评估时要追问"这个模型/agent 能触达哪些工具和下游系统"。
- **Responsible AI（RAI）风险是光谱而非二元判定**：偏见、伦理类问题通常主观且依赖上下文，不像传统渗透测试的成功/失败二元结果。涉及这类发现时要求多学科视角（安全 + AI 伦理 + 社会科学），且不能用二元"漏洞已验证"的口径去套。
- **业务影响框架（Unit 1.2.3）**：把技术发现翻译成业务风险陈述，即"技术缺陷 → 可能触发的业务后果（财务/合规/声誉）"，用于向管理层汇报和驱动补救优先级排序。产出报告时优先用这种句式，而不是停留在技术描述层面。
- **三套组织框架**（每套服务不同目的，组合使用）：
  - **MITRE ATLAS**：把 ATT&CK 扩展到机器学习领域，提供跨训练/推理/部署阶段的对抗技术分类法和统一词汇，用于给发现打标签、对齐报告术语。
  - **OWASP Top 10 for LLMs**：应用层风险清单（如 prompt injection、不安全输出处理、RAG 配置错误、数据泄露），为红队提供"测什么"的类别清单，为蓝队提供对应缓解点。
  - **NVIDIA AI Kill Chain**：把攻击活动按 Recon → Poison → Hijack → Persist → Impact 排序，用于组织攻击链叙事、识别防御可以在哪一环节打断攻击。
- 用法建议：拿到目标后，先用 ATLAS 给已知/怀疑的技术打标签，用 OWASP 类别核对是否遗漏了某类应用层风险，再用 Kill Chain 的五阶段组织攻击叙事和报告结构。

### 1.3 小结与承上启下

- 本节是纯定位性总结：AI 安全需要专门方法，是因为价值形态变了（行为而非静态文件）、持久化机制变了（数据/记忆投毒而非传统后门）、攻击者影响力被自主行为放大了。
- 三个框架（ATLAS/OWASP/Kill Chain）是贯穿全课程的组织工具，不是本章独有内容，后续每个章节 skill 在给出具体技法时都应引用对应框架类别，保持汇报口径一致。
- 下一步：把这里建立的框架应用到具体侦察和威胁建模上，衔接 [[recon-ai-targets]] 与 [[target-reconstruction-engagement]]。

## 验证标准

本 skill 本身不产生"漏洞发现"，而是产生"目标定位判断"和"框架选择"，因此验证标准分两层：

- **定位是否成立**：给出的攻击面分类（单 agent / 多 agent / RAG / MCP / 供应链 / 云容器）是否有实际证据支撑（服务清单、架构文档、初步探测结果），而不是凭猜测分类；分类错误会导致路由到错误的章节 skill，浪费后续验证成本。
- **框架映射是否成立**：引用 ATLAS 技术编号、OWASP 类别、Kill Chain 阶段时，必须对应到本次任务实际观察到的行为或计划中的动作，不能为了"看起来专业"而硬贴标签。
- 明确区分：本 skill 产出的"这是 RAG 攻击面""这属于 OWASP 某类风险"是分类判断，不是漏洞验证；具体漏洞是否成立，由被路由到的下游技法 skill 按其自身验证标准判断（工具调用成功 ≠ 目标端确有效果 ≠ 发现已验证）。

## 常见失败与规避

- **把云端商用聊天助手（如公开的 ChatGPT/Claude 网页版）当作目标**：课程明确这不是范围内目标，未获授权不得测试；红队工作应聚焦企业自建/自部署的 agent、RAG、编排、托管、供应链等企业 AI 攻击面。
- **用二元漏洞判定套用 RAI/伦理类发现**：偏见、误导性输出等问题是光谱式的，需要多学科评估语言，不能简单标"通过/不通过"。
- **报告停留在技术层，不做业务影响翻译**：会导致管理层无法评估优先级；应按 Unit 1.2.3 的业务影响框架把技术发现转成财务/合规/声誉后果陈述。
- **不做框架标注，凭感觉描述攻击链**：会导致跨团队沟通成本上升；应坚持给每个发现打上 ATLAS 技术标签、OWASP 类别、Kill Chain 阶段这三重标注。

## 证据与报告

- 目标分类判断的依据：架构文档摘录、初步端口/服务枚举结果、公开信息来源，注明来源与时间。
- 框架映射记录：对每个发现/计划动作，记录对应的 MITRE ATLAS 技术 ID（如可确定）、OWASP Top 10 for LLMs 类别、NVIDIA AI Kill Chain 阶段（Recon/Poison/Hijack/Persist/Impact）。
- 业务影响陈述：技术发现 → 潜在业务后果（财务估算范围、合规条款、声誉影响）的对应关系，供 capstone 阶段（[[capstone-full-chain]]）和证据报告链路引用。
- 严禁把测试靶场的真实 IP、主机名、凭据、密钥写入报告示例；所有示例需泛化表达。
