## 概述与何时用

本 skill 覆盖主体资料 Supply Chain Attacks on AI/ML Systems 的三个 Learning Unit：8.1 代码执行攻击、8.2 模型与数据篡改攻击、8.3 规避技术；对应下方"方法与技法"分节。资料结构本身只有这三节，没有单独编号的 8.4，如需要一个收敛性的"验证/防御总览"，见本文件末尾各段的整合说明——**待确认项见文末**。

供应链攻击的核心前提：不直接攻击目标本身，而是攻击目标已经信任并加载的上游组件——序列化模型文件、MCP 服务器/助手扩展代码仓库、包索引、微调数据集、量化产物。一旦该组件被加载或执行，攻击者获得与加载者同等的执行/影响能力。

适用场景：
- 目标团队从公共模型仓库（如 Hugging Face 类平台）、内部 GitLab/包索引拉取模型或依赖，缺少强制的完整性校验。
- 目标使用 MCP 服务器、Agent 扩展或类似"技能/插件"机制，多部门共享同一份源码仓库。
- 目标有微调/LoRA 训练管道，且训练数据或适配器来自外部或权限较低的协作者可写入的位置。
- 目标部署了自动化恶意代码/模型扫描（picklescan、AI 辅助分类器等），需要评估其规避面。

## 在 SOP 中的位置

在「枚举→攻击→检测→规避」总流程中，本 skill 主要覆盖**攻击**（通过污染上游组件获得执行/行为篡改）与**规避**两个阶段，前置依赖枚举阶段先确认攻击面。

- 前置：先用 [[recon-ai-targets]] 确认目标是否存在模型托管、包管理、CI/CD、MCP 服务器仓库等供应链入口；无法先枚举清楚"加载点在哪、谁能写入、谁会加载"就直接尝试投毒，属于跳过证据链。
- 若目标本身是 MCP 服务器且攻击面是工具描述/权限而非源码仓库投毒，主体技法路由到 [[attack-mcp]]；本 skill 只覆盖 MCP **供应链**（源码仓库被植入后门）场景。
- 若目标是 agent 的记忆或 RAG 索引投毒（运行时投毒，而非训练/微调数据投毒），路由到 [[attack-single-agent]]（记忆攻击）或 [[attack-rag-pipelines]]；本 skill 聚焦训练/微调阶段的数据与权重篡改。
- 下游：确认代码执行或模型行为篡改已生效后，后续横向移动/云容器利用衔接 [[cloud-and-container]]；需要重建目标拓扑和交战边界时衔接 [[target-reconstruction-engagement]]。
- 汇报时用 MITRE ATLAS 的 ML Supply Chain Compromise 技术类别和 NVIDIA Kill Chain 的 Poison/Persist 阶段标注发现，参见 [[ai-security-landscape]]。

## 方法与技法（按小节）

### 8.1 代码执行攻击

- **反序列化 RCE（pickle/joblib/torch.load 家族）**：确认目标是否用 `torch.load()`（默认 `weights_only=False`）、`joblib.load()`、`pickle.load()`、`pandas.read_pickle()` 等加载来源不受信的文件。这些函数在反序列化时会实例化任意类并调用其方法；若被加载对象定义 `__reduce__`，反序列化过程会执行其返回的可调用对象（典型如 `os.system()`）。方法：构造一个定义 `__reduce__` 返回危险调用的类，序列化后以命名/版本号伪装成合法产物（如仿真 checkpoint 命名规则，使其在"取最高版本/最新时间戳"的自动加载逻辑中被优先选中），投放到目标会加载的共享路径（模型仓库、共享目录、CI 产物区）。观察：能否建立回连（reverse shell）、能否读取加载进程的凭据/环境变量。
- **跨序列化格式的同类风险**：`joblib`、`pandas.read_pickle` 等一切内部包装 pickle 的库都同样脆弱；TensorFlow SavedModel 的计算图可包含 `tf.io.read_file()`/`tf.py_function()` 等在加载时执行的算子；ONNX 本身不允许任意代码执行，但外部数据引用路径可被滥用做路径穿越读写。评估目标加载管道时，逐一确认使用的序列化格式属于哪一类风险，不要只检查 `.pt`/`.pkl` 后缀。SafeTensors 等"仅存张量数据"的格式设计上排除了此类风险，可作为对比基线。
- **MCP/助手扩展供应链投毒**：先做常规侦察确认目标框架（如某 MCP SDK）、装饰器/注册模式、工具描述格式，使植入的后门代码风格与现有代码一致、难以在 diff 中被一眼识别。方法：在已获得的仓库写权限范围内，向被多个下游 agent/工作站共同依赖的辅助模块中植入后门逻辑，使其在正常工具调用路径（而非新增可疑函数）中触发。风险控制：仅在已确认的授权范围和已声明的仓库权限内操作，不扩大到未授权仓库。
- **依赖生态混淆（Dependency Confusion）**：确认目标内部私有包名是否可能与公共包索引命名冲突；若包管理配置未显式锁定私有源优先级，构造同名但版本号更高的公共包可能被优先安装。观察：安装/构建日志中拉取的包来源与版本，验证是否命中混淆而非单纯理论可行。

### 8.2 模型与数据篡改攻击

- **训练数据投毒植入持久后门**：目标是让微调后的模型在特定触发条件下产出攻击者想要的内容（如泄露的密钥、特定命令、不安全代码模式），而非直接执行代码，因此更难被文件完整性监控、AV/EDR 发现。方法：先跑通并记录"干净模型"的基线输出，再构造少量恶意样本并按适当比例（放大重复）混入训练/微调数据集，之后正常触发再训练/微调流程。观察：重训后模型在触发条件下的输出是否稳定复现植入行为，且不影响正常输入下的表现（即投毒具有条件性、非全局性）。
- **风险控制（红队纪律）**：修改任何生产/共享模型前，必须已获得针对该模型的明确授权或确认其在交战范围内；操作前备份干净版本，便于验证影响并可回滚。未授权微调可能导致模型对齐/安全防护退化、下游服务中断，且难以逆转。
- **隐蔽化投毒模式**：比起硬编码密钥这类"显眼"投毒，更隐蔽的做法是让模型倾向于生成含已知缺陷模式的代码（引用有 CVE 的过时库、不安全默认配置、认证逻辑中的细微缺陷），这类输出更容易通过人工审查和自动扫描。进一步地，可训练为条件触发的"sleeper" 行为——正常条件下表现正常，仅在特定关键词/日期/环境标志下激活；这类行为对常规 RLHF/对齐再训练具有一定抗性，评估时应说明这是研究已证实的现象（不代表可在任意目标稳定复现）。
- **LoRA/适配器投毒**：相较全量微调产生的大文件，LoRA 类适配器体积小、分发方便、常被当作"只是权重"而缺乏审查，是有吸引力的供应链投毒面。方法：确认目标是否从外部/低权限协作者处拉取适配器并直接加载合并；若是，评估植入被污染适配器（含触发式行为）并使其进入正常分发/加载路径的可行性。
- **量化产物的验证缺口**：量化（降低权重精度以压缩/加速）会不可逆地改变每个权重的二进制内容，导致量化后文件哈希与原始模型哈希无数学关联，无法用哈希比对验证"这个量化产物确实来自声称的源模型"。评估目标是否依赖第三方量化产物但缺乏可信的溯源/签名链，这是一个可利用也可作为发现汇报的验证缺口。
- **分词器篡改**：不修改任何权重或代码，仅篡改分词器映射（如让某个安全分类结果词元被错误解码），可使"AI 辅助安全扫描器"在模型判断正确的情况下因输出解码错误而 fail-open（默认判为安全）。方法：定位分类流水线中"模型判断 → 关键词匹配裁决"的环节，评估分词器完整性是否被校验；若未校验，改动可以极小（一次词元映射调整）且对良性输入无副作用。这是一种极难被常规代码/权重审计发现的攻击面，因为源码和权重都未改动。

### 8.3 规避技术

- **绕过 pickle 类扫描器（如 picklescan）**：这类扫描器通常只检查 opcode 层面的 `GLOBAL`+`REDUCE` 组合是否命中已知危险导入（如 `os.system`），不分析被反序列化对象的完整 Python 逻辑。技法一：把危险调用移出 `__reduce__` 的直接返回，改为返回"类自身 + 状态字典"，让状态恢复（`__setstate__`/`BUILD`）阶段才真正执行危险操作——但这要求目标机器上存在该类定义（例如配合依赖投毒预先植入，或攻击者与目标在同一环境构造/加载）。技法二（跨机器可用）：寻找目标环境中已安装、未被扫描器加入黑名单、且内部会对参数调用 `eval`/`exec` 而不做校验的"gadget 函数"（如某些数学/科学计算库的表达式求值入口），以合法函数名出现在 opcode 中从而绕过基于黑名单的静态检测。评估这类 gadget 时需确认：常见于目标技术栈、不在扫描器黑名单、内部确实无过滤地传给危险原语。
- **分层规避（对抗代码审查 + SAST + 沙箱）**：代码审查读源码、SAST 扫描危险函数名/导入模式、沙箱在隔离环境执行观察行为——三层检测各自独立，只绕过一层不足以过关。组合技法：把有效载荷加密/编码为不含可识别字符串的二进制数据文件（源码和字符串扫描均无法命中）；将触发/引导代码编码为零宽度 Unicode 字符藏入源文件（人工 diff 和常规 SAST 均不可见，只能通过扫描 U+200B–U+200F 区间字符或 Unicode 归一化后比对长度发现）；载荷在检测到虚拟化/调试器/容器等分析环境特征时拒绝执行（对抗沙箱动态分析）。三种手段任一单独使用都会被其对应的检测层识别，组合使用才具备对全检测栈的抗性。
- **环境绑定与隐写**：将解密密钥绑定到目标特有指纹（主机名、MAC 地址等），使载荷只在预期目标上正确解密，其余环境中呈现为随机数据，降低批量沙箱检测命中率。可将载荷隐写进合法二进制文件（模型权重、图片、字体）以规避基于文件类型的扫描。多用途文件格式（polyglot）利用格式歧义进一步增加静态分类难度。
- **信任与校验绕过**：评估目标是否仅依赖文件名/版本号排序（如"取 epoch 数最高的 checkpoint"）而非密码学签名来决定加载哪个产物，这类逻辑可被用更高版本号命名的恶意文件劫持优先加载顺序。

### 8.4 技战法编排：围绕制品生命周期定位执行与篡改点（实战综合；非课程原文）

为模型、适配器、分词器、数据集和插件建立生命周期链：**获取 → 缓存 → 校验 → 解析/反序列化 → 注册 → 加载 → 推理/训练 → 再发布**。逐跳记录制品标识怎样变化，以及代码或异常行为发生在导入时、加载时、首次推理时还是特定输入时。

先用无害标记区分四类效果：加载即执行、初始化钩子执行、特定输入触发的行为篡改、受影响制品被缓存/镜像/再发布形成传播。不要把“制品被接受”直接当成“执行已发生”。

采用版本差分与消融：固定环境和测试集，只替换一个制品；再分别替换权重、LoRA、tokenizer、配置、预处理和依赖锁文件，定位最小致因组件。行为篡改至少同时跑正常集、触发集、邻近触发变体和随机对照，报告攻击成功率与正常能力下降，避免把普遍退化误判为精准后门。

组合打法：

- **信誉操纵 → 制品进入流水线 → 加载触发**：由 `supply-chain-reputation` 验证选择链，再由本 skill 验证真实加载行为。
- **数据投毒 → 微调/训练 → 触发行为**：保存投毒前数据、实际训练输入、生成制品摘要和触发结果，证明因果链没有在预处理阶段断裂。
- **分词器变化 → token 映射偏移 → 定向触发**：同一字符串在基线和篡改分词器下分别记录 token 序列。
- **制品解析 → 代码执行 → 二次篡改**：把取得执行与随后修改权重/配置拆成两个发现分别验证。

## 验证标准

- **工具/载荷执行成功 ≠ 漏洞已验证**：拿到反弹 shell、扫描器报"clean"、或看到重训模型输出符合预期，都只是链路中一步的证据；必须证明该结果发生在目标声明的真实加载/执行路径上（而非攻击者本地环境自证）、且非预期行为对目标业务确有影响，才能算发现已验证。
- **反序列化/依赖投毒类**：需要证据显示目标进程/自动化流水线确实加载了投放的文件并执行了载荷（如目标侧建立的回连会话、目标环境变量/用户名回显），而不仅是本地构造成功。
- **模型/数据篡改类**：需要"投毒前基线输出"与"投毒后触发条件下输出"的对比记录，证明变化具备可复现性、条件性（不影响正常输入），且确认改动确实来自本次投毒而非环境噪声。
- **规避类**：需要展示扫描器/分类器/沙箱在有效载荷存在的情况下仍判定为安全（阴性结果记录），并说明规避对良性样本无副作用（不能只展示对恶意样本的绕过而未验证误报率不变）。
- 所有验证需在已获授权的靶场/环境内完成；修改共享或生产模型前必须确认授权范围覆盖该资产。

## 常见失败与规避

- **只在攻击者本地验证 pickle 载荷能触发 `__reduce__`，未确认目标真实加载路径会执行**：本地成功不等于目标环境会执行；需确认目标的加载函数、参数（如 `weights_only` 设置）和触发条件一致。
- **`__setstate__` 绕过技法误用于跨机器场景**：该技法依赖目标机器上存在攻击者定义的类，脱离依赖投毒或同环境构造的前提会直接因 `ModuleNotFoundError` 失败；跨机器场景应选用已安装库内的 gadget 函数。
- **只做单层规避（比如只加密字符串）就宣称"绕过检测"**：代码审查、SAST、沙箱是独立检测层，展示规避效果时必须说明针对哪一层、是否验证了组合场景。
- **训练数据投毒后未做"干净基线 vs 投毒后"对比**：容易把模型本身的随机性或已有缺陷误判为投毒效果；必须先记录基线。
- **把量化哈希不匹配当作"投毒证据"**：量化本身就会导致哈希不可比对，这是设计层面的验证缺口而非投毒信号，报告中应明确区分"缺乏验证能力"和"已证实被投毒"。
- **未经授权修改共享/生产模型**：即便技术上可行，也可能造成不可逆的对齐/安全退化和业务中断，属于默认拒绝范围，必须先确认交战范围。

## 证据与报告

- 反序列化类：载荷生成脚本（泛化，不含真实目标凭据/IP）、投放路径与命名策略、目标侧回连会话记录（用户名/主机标识可脱敏保留结构）、opcode 反汇编结果（证明危险调用链）。
- 供应链/依赖投毒类：涉及的仓库/包名（脱敏后的结构性描述）、写入权限来源、被污染文件在正常调用路径中的触发方式记录。
- 模型/数据篡改类：投毒前后的输出对比记录、投毒比例与样本构造方式、重训练/微调触发方式、影响范围评估（是否仅在触发条件下激活）。
- 规避类：分层检测各自的判定结果（源码扫描/SAST/沙箱/AV 分类器）在载荷存在前后的输出，证明每一层均被绕过而非只测了一层；对良性样本的检测结果保持不变的记录，避免"提高误报率"被误报为"规避成功"。
- 所有证据材料须脱敏处理靶场专属 IP、主机名、凭据、密钥；示例一律使用泛化占位符。
