## 超课程范围说明

本 skill **不在** 主体资料 66 个技术点覆盖范围内。该部分只覆盖反序列化代码执行（8.1）、训练数据/LoRA/分词器篡改（8.2）与检测规避（8.3），未涉及包/模型的信誉信号操纵、抢注命名或刷量。本文内容依据 OWASP LLM03（Supply Chain）、MITRE ATLAS 中 ML Supply Chain Compromise 相关战术、以及 NIST AI RMF 供应链治理要求蒸馏泛化，属于对 [[code-exec-and-tampering]] 的补充延伸，而非课程原文转译。

## 概述与何时用

供应链信誉攻击不依赖代码执行或权重篡改，而是操纵**人和自动化流程用来判断"这个上游组件是否可信"的信号**：包名/模型名与合法项目的相似度、下载量、评分、维护者身份、发布时长。核心前提是开发者和 CI 流程普遍用这些信号做"要不要引入"的快速判断，而这些信号本身可被低成本伪造或诱导产生。

适用场景：
- 目标团队的开发流程包含"让 LLM 推荐/生成依赖包名或 MCP Server 配置，再直接安装"这一步，且未做人工核实包是否真实存在。
- 目标从公共模型仓库、包索引、MCP 市场选型时，主要或仅依据下载量、星标数、评分排序，缺少独立的来源核实流程。
- 需要评估"一个新发布不久、信誉信号却异常良好的制品"是否值得进一步怀疑。
- 需要向目标说明"良好的下载量/评分本身不能替代身份与完整性验证"这一治理缺口。

## 在 SOP 中的位置

在「枚举→攻击→检测→规避」总流程中，本 skill 覆盖**枚举**（识别信誉操纵信号、判断命名空间是否可疑）与**攻击面评估**（说明操纵路径的可行性），刻意不覆盖"发布真实恶意制品"这一步——见下文"验证标准"与边界说明。

- 前置：先用 [[recon-ai-targets]] 确认目标团队使用哪些包索引/模型仓库/MCP 市场，以及其内部是否有依赖引入审批流程。
- 若已确认某个仿冒制品内嵌反序列化载荷或篡改过的权重，具体攻击技法路由到 [[code-exec-and-tampering]]（8.1 反序列化、8.2 模型/数据篡改）；本 skill 只覆盖"如何让目标信任并选择安装它"这一前置的信誉操纵环节，两者衔接但不重复。
- 若目标场景是 MCP 服务器的工具描述/权限滥用（而非市场层面的仿冒发现），路由到 [[attack-mcp]]。
- 汇报时用 MITRE ATLAS 的 ML Supply Chain Compromise 相关技术类别标注发现，参见 [[ai-security-landscape]]。

## 方法与技法

### 识别信号：命名空间是否可疑

- **命名相似度检查**：对比目标即将引入的包/模型/MCP Server 名称与已知合法项目名称的编辑距离、常见拼写变体（连字符/下划线互换、单复数、常见前后缀如 `-official`、`-ai`、`-mcp`）、以及是否为知名项目名加机构/团队前缀的仿冒组合。命名相似不等于恶意，但相似度异常高且发布方与原项目无关联时构成可疑信号。
- **是否真实存在于官方索引**：先确认包/模型名是否确实存在于对应权威索引（如公共包索引、Hugging Face 类模型托管、MCP 官方或社区市场），还是仅出现在 LLM 生成的建议、博客、论坛帖子中——后者是 slopsquatting 的典型触发点：模型产生看似合理但不存在的包名，攻击者提前抢注该名称，等待开发者复制 LLM 建议直接安装。评估时用最基础的核实动作（在索引官方搜索接口查询该确切名称）区分"模型幻觉出的名字"与"确实存在的包"。
- **注册时间与发布历史**：核对制品/维护者账号的首次发布时间、版本发布频率、是否在短期内从零骤增到大量版本或大幅体积变化。距今很近才注册、且短时间内集中冲量的账号/命名空间比长期稳定维护的项目更值得复核。
- **下载量/评分/星标异常**：关注短期内下载量或评分陡增但缺乏对应的社区讨论、issue、外部引用支撑的情况；关注评论/评分是否高度集中在极短时间窗口内、措辞高度相似（Reputation Inflation 的典型刷量特征）。
- **维护者信誉与账号关联**：核实维护者账号的历史发布记录、是否与已知合法组织有可验证的关联（如域名验证、组织认证标记），还是新建账号、无历史记录、或冒用与知名维护者相似的用户名。
- **Rug Pull 模式**：对于已被广泛使用一段时间的包/模型，关注其维护者是否发生过所有权转移、新版本行为是否与历史版本存在未在变更日志中说明的显著差异（新增网络请求、新增依赖、权限范围扩大）——这类"先建立信誉再变更行为"的模式在长期活跃制品上比在新制品上更隐蔽，需要版本间行为对比而非仅看当前版本。

### 技战法编排：从候选名称到选择链路验证

供应链信誉攻击的验证对象不是“某个名字像不像”，而是**目标的选择流程能否被伪造信号稳定推动**。按以下链路组织测试：

1. **候选生成面**：分别从 LLM 推荐、代码补全、搜索结果、市场排序和示例配置中收集候选名称，记录同一任务多次生成时哪些不存在名称会重复出现。重复幻觉比单次随机名字更适合作为 slopsquatting 风险信号。
2. **相似名称族**：围绕合法项目构造只改变一个特征的候选集——拼写距离、分隔符、组织前缀、生态后缀、维护者显示名。一次只改变一个变量，测出真正影响选择的视觉或语义特征。
3. **信誉信号剥离**：用同一制品描述制作多组等价候选，分别只保留下载量、评分、发布时间、组织标记、README 质量或模型卡完整度，观察目标人员或自动流程究竟依赖哪个信号。
4. **排序位次测试**：保持元数据相同，只改变候选在列表中的位置、是否带“推荐/热门”标签、是否出现在 LLM 回答首项，测量首位偏差和自动选择倾向。
5. **选择与执行分离**：先验证目标会把候选加入配置、锁文件草案或安装计划，再单独验证后续是否真的解析和获取该制品。不要用“点击了搜索结果”代替“依赖已进入交付链”。

对 Rug Pull 场景使用**版本差分打法**：选取一个历史稳定版本作为基线，对后续版本逐项比较入口脚本、依赖图、网络目的地、模型加载钩子、反序列化路径和默认配置。优先寻找“维护者/所有权变化”与“行为变化”在时间上紧邻的版本，而不是只扫描最新版。

建立可复用的信号评分，而不是凭直觉判定：`名称近似度 + 身份关联缺失 + 时间异常 + 热度异常 + 版本行为突变 + 外部引用缺口`。评分只用于排序调查优先级；最终验证仍需回到目标选择链路和制品行为。

### 可用工具

- **`package_reputation_check`**：只读查询工具，用于核实指定包/模型名称在 npm、PyPI、Hugging Face 等公共索引中的存在性、发布时间、维护者信息、下载量等公开元数据。用途仅限**核实与取证**——确认某个名称是否真实存在、其信誉信号是否与预期匹配，而不用于下载或安装被核实对象本身。发现命名可疑或信号异常后，应以该工具的查询结果作为报告证据的一部分。

## 验证标准

- **区分"发现可疑命名空间"与"确证恶意制品"**：命名相似、注册时间新、下载量/评分异常，都只是**信号**，说明存在被信誉操纵利用的可能性，不等于该制品已被证实包含恶意代码或行为。确证恶意需要额外证据（如实际检出的恶意载荷、已记录的社区报告、厂商公告），这类深入分析不在本 skill 范围内，需衔接 [[code-exec-and-tampering]] 或专门的静态/动态分析流程。
- **发现已验证的判定标准**：至少满足——（1）该名称在权威索引中确实存在且可被安装/加载（排除单纯的 LLM 幻觉误判）；（2）其信誉信号（发布时间、下载量、评分、维护者关联）经核实后确与已知合法项目不一致或存在刷量特征；（3）已记录具体的核实证据（工具查询结果、时间戳、截图或原始响应），而非仅凭直觉判断"看起来可疑"。
- **不构成验证的情况**：仅凭名称与知名项目相似就直接判定为恶意；未实际查询索引元数据就基于经验假设"这个包应该是假的"；把正常的新项目冷启动阶段（新发布、下载量低）等同于恶意信号。

## 常见失败与规避

- **把"命名相似"直接等同于"确证仿冒"**：命名空间冲突在正常生态中也会自然发生（同名不同用途、独立重名项目），必须结合发布时间、维护者关联等多个信号交叉验证，避免单一信号误判。
- **只看当前快照，不做时间序列对比**：Rug Pull 类信号必须靠历史版本/历史元数据对比才能发现，仅看当前版本容易漏判"信誉建立后行为突变"。
- **把攻击者视角的可行性分析当作已完成的攻击**：本 skill 覆盖"评估该操纵路径是否可行"，不代表已经执行；报告中需明确说明是理论评估还是已有实证。

## 边界：只读侦察，不发布恶意制品

本 skill 严格限定为**只读侦察与信号核实**：查询公共索引元数据、比对命名相似度、评估目标团队的信任流程缺口。**发布仿冒包、伪造下载量/评分、上传含恶意载荷的模型或 MCP Server 等制品到公共或目标使用的仓库/市场，属于越界行为，不在本 skill 授权范围内，不执行**。如需验证"目标是否会真的安装 LLM 幻觉出的不存在包名"这类假设，应通过已获授权的受控环境模拟（如在内部隔离索引中操作），而非面向真实公共生态发布任何制品。

## 证据与报告

- 命名相似度分析记录：目标引入的名称、疑似仿冒对照的合法项目名称、相似度评估依据。
- `package_reputation_check` 查询结果：存在性、注册/发布时间、维护者信息、下载量与评分的原始查询记录（含查询时间戳）。
- 时间序列对比记录（如涉及 Rug Pull 评估）：不同版本间的行为/依赖/权限差异说明。
- 明确标注：本次发现属于"信号异常，建议进一步核实"还是"已确证恶意"，避免报告中混淆两者置信度。
- 涉及目标真实依赖名称、内部仓库结构的部分须脱敏，仅保留结构性描述。
