## 概述与何时用

本 skill 覆盖"总装配"章节：一次真实交战往往不是单一技术的胜负，而是**一条链**——公网 AI 功能拿到立足点 → 传统基础设施（网关/RDP/数据库）做横向 → 内网枚举挖出更多凭据 → 域接管。链条中 AI 专项漏洞（提示注入、工具滥用、RAG/agent 越权）和传统红队技术（RDP 网关穿透、SQL 提权、共享枚举、内存取证、计划任务提权）是同一条业务链上下游，彼此喂料：AI 漏洞给你第一枚立足点和凭据，传统技术把凭据变成更深的立足点，新立足点又暴露新的 AI 组件或新凭据。

适用信号：任务范围横跨"公网站点/AI 功能 + 多个内网网段/域"；只给了很少情报（一个可达 IP、几个 CIDR），要求你自己重建拓扑；验收目标是终态权限（Domain Admin/核心数据），而不是某一步的工具调用成功。

场景已泛化（MegaCorpOne AI 场景），不含真实 IP/凭据/主机名。

## 在 SOP 中的位置

对应总 SOP（枚举→攻击→检测/验证→规避）在**交战级别**的编排：本 skill 不是新增技法，而是决定"什么时候切换到哪个专项 skill、什么时候切回传统内网渗透"。典型编排顺序：

1. 情报重建 + 交战规划 → 参考 `target-reconstruction-engagement`（10.1/10.2 的目标重建与信任区/提权规划方法）。
2. 公网枚举与 AI 功能识别 → 参考 `recon-ai-targets`（被动/主动侦察）+ `ai-security-landscape`（AI 攻击面分类）。
3. 攻破公网 AI 功能拿立足点 → 参考 `attack-single-agent`（直接/间接提示注入）与 `attack-mcp`（工具越权）。
4. 传统横向（网关、RDP、数据库、共享） → 本 skill 正文给方法，非 AI 专项 skill 覆盖范围。
5. 内网再遇到 AI/agent/RAG 组件（如内部知识库助手）→ 切回 `attack-rag-pipelines`、`attack-a2a-multi-agent`。
6. 全程遵循 `ai-redteam-methodology` 的枚举→攻击→检测→规避总纪律，并把发现证据交给报告环节。

## 方法与技法（按小节）

### 11.1 场景与拓扑重建
- 交战通常只给"一个外部可达点 + 若干内网 CIDR"，没有网络图、没有主机名清单；把这当作正常起点，不要求先拿到完整拓扑才开始。方法：先明确 RoE 里的隐蔽性/最小干扰约束（是否有主动监控的 SOC、是否允许修改服务但要求可回滚），据此选端口、载荷投递方式、是否需要与合法流量混淆。
- 交战前准备可复用的载荷基础设施（一次性反弹 shell + 持久化 C2 信标 + 加密/混淆隧道工具），而不是每个立足点现造一次；载荷生成、C2 框架选择本身可替换（任意团队可用的框架），重点是"提前备好、按需复用"这个流程习惯。
- 每次修改目标系统状态（加组、启用服务、关闭 AV/EDR 某功能）都要记录，为后续清理和报告留痕——这是纪律而不是可选项。

### 11.2 公网站点枚举与利用
- 先做功能识别：浏览公网站点，定位 AI 驱动的功能点（聊天助手、搜索增强等），用直白提问摸清模型/系统提示/工具能力边界，再决定是否需要规避手段（多语言、编码混淆）。
- 若发现 AI 组件能触发后端工具（如数据库查询工具）且工具执行与 LLM 决策之间没有二次校验，尝试用自然语言注入让其代其执行超出预期范围的操作（例如从只读查询升级到配置类/命令执行类操作）；这类攻击方法与 `attack-single-agent`（直接提示注入、工具滥用）重合，本 skill 只强调它是"外网入口"这一角色。
- 拿到命令执行后，用系统内建方式确认操作系统与当前身份，再落地一个用户可写目录下的载荷并建立回连，形成第一个立足点；同时枚举该立足点对内网其他主机的可达性（如内建远程管理协议），寻找同网段/相邻网段的下一跳。
- 立足点主机上的应用配置文件、连接字符串、密钥类文件是常见的横向燃料——枚举可读的配置目录，注意其中的服务账号明文凭据。

### 11.3 经 RDS/远程网关横向
- 用上一步拿到的账号所在的组成员关系（如某个允许远程访问的组）判断是否能通过网关类设备（RD Gateway 等）RDP 进入另一个域/网段；连接时挂载本地目录做文件传输通道。
- 到达网关后，枚举网关的访问策略对象（如 RAP/资源授权策略），确认它桥接到哪个域、哪些主机组，并结合域内组描述字段找出哪些账号被允许穿越网关——很多环境会在组描述里意外记录用途说明，是低成本的信息源。
- 新立足点上，检查代码托管/CI 类内部服务的历史分支或配置差异（如不同分支下的数据库连接字符串），这类"开发环境遗留凭据"往往指向另一个数据库实例和新的服务账号。
- 用拿到的数据库账号确认权限级别（是否等价 sysadmin），若有则可通过数据库自带的命令执行通道（如启用后再禁用的高危存储过程）落地信标、建立隧道，并在结束后主动关闭该通道以降低足迹。
- 二进制/客户端工具（数据库管理插件等）里的硬编码凭据是常见的"父域账号泄漏点"——账号前缀/命名空间能提示它属于父域还是当前子域，判断优先级。

### 11.4 内网枚举
- 深入网络后优先用系统内建、不额外落地二进制的方式做域枚举（如通过 LDAP 查询类型加速器直接查询域控、组、计算机对象），而不是常被 EDR 标记的传统枚举工具；目的是既拿到域控/计算机清单，又降低被检测面。
- 用已获得的凭据枚举文件共享，注意"能读"和"能写"的共享分开记录，一个可写共享往往是下一步供应链式攻击（替换脚本、投毒依赖模块）的落点。
- 若共享中的自动化脚本会被定时任务/其他服务账号执行，评估篡改该脚本或利用其依赖加载机制（如脚本语言的模块搜索路径劫持）实现代码执行——这类"供应链内的执行权转移"是本节的核心技法之一，效果是从"文件写权限"换成"另一个账号的执行权"。
- 触发执行后，从该账号的进程内存中提取凭据（如对使用本地凭据库/密码管理器的进程做内存转储再离线搜索明文字符串），常能拿到该账号对其他共享/系统的写权限凭据，形成账号权限的滚雪球式提升。
- 每新增一个持久化落点（信标、隧道、转储文件）都要记入清理清单。

### 11.5 域接管
- 用滚雪球拿到的账号继续枚举更高权限共享，寻找管理员个人文件（SSH 私钥、命令历史）——命令历史常常意外记录密钥生成时用过的口令/参数，是从"有私钥"到"能解密私钥"的关键一环。
- 若目标主机存在计划任务由更高权限账号（含机器账号/SYSTEM）执行且任务指向的二进制路径可被当前权限覆盖，替换该二进制为载荷，等待任务触发即可拿到该权限的会话——这是本地提权到 SYSTEM 的常见路径，不依赖内存漏洞。
- 内网中若存在面向员工的知识库/RAG 助手，且其文件读取类工具没有路径限制，可通过间接提示注入诱导它读取并回传范围外的文件（如另一账号的私钥）——这一步是 AI 专项技法，方法归属 `attack-rag-pipelines`/`attack-a2a-multi-agent`，本 skill 只标注它在链路中的位置：内网阶段的第二个 AI 突破口。
- 用拿到的密钥/口令尝试对该账号在域内可能存在的其他主机的等效访问（同一账号在多主机复用非默认管理端口的场景很常见），验证是否落在域管理员/企业管理员组，以此作为域接管的最终验证点。

### 11.6 收尾：AI 与传统链路的因果关系
- 复盘时明确标出链路中真正的"AI 专项弱点"节点（如：AI 功能对话与后端工具执行之间缺少二次校验、agent 文件类工具没有路径范围限制）和"传统弱点"节点（网关访问策略配置、明文凭据留存、计划任务权限配置、可写共享+脚本依赖劫持）。二者缺一不可——AI 弱点给了初始/内网的两次突破口，传统弱点把这些突破口连成了通往域控的完整路径。
- 报告里针对每个 AI 突破口给出对应的收敛建议方向(工具调用允许/拒绝列表、执行前用户确认、工具可访问路径的强约束)，针对传统突破口给出对应的基础设施加固方向；这体现"AI 系统与传统 IT 基础设施同属一条业务链"，修复也必须两边同时做，只堵 AI 侧或只堵传统侧都无法切断链路。

### 11.7 技战法编排：用状态转移证明完整攻击链（实战综合；非课程原文）

把完整链路写成状态机，而不是命令时间线：`无立足点 → 可与 AI 接口交互 → 获得代码/工具执行 → 获得新网络位置或身份 → 发现关键资产 → 控制目标资产`。每次状态转移记录转移前能力、最小必要技法、转移后新增能力、原始证据以及移除该技法后是否仍有等价路径。

同步维护两张图：**能力图**记录当前可读、可写、可执行、可委派和可到达对象；**证据图**把每项能力连接到产生它的请求、响应、日志或目标端状态。下一步只选择能新增关键能力或验证关键假设的动作。

组合链必须说明 AI 增益是否必要：信息泄露怎样缩短传统枚举，工具执行怎样改变身份或网络视角，RAG/记忆/A2A 投毒怎样影响后续用户或任务；后续若完全依赖传统漏洞，应与 AI 初始突破分开归因。

对关键转移做一次从干净状态开始的最小重放，删除侦察阶段的试错和无关命令，只保留必要步骤。最小重放用于证明因果关系，并形成最终可交付复现链。

## 验证标准

区分三个层级，链路越长越要在每一环写清楚落在哪一级：
- **工具调用成功**：命令/查询/请求返回了"success"类响应，但未确认目标端真实状态变化（例如聊天接口回复"executed successfully"不等于命令确实落地）。
- **目标端确有效果**：能独立复现的证据显示状态确实改变（如回连 shell 建立、新增的域组成员关系可被后续查询确认、共享文件确实被替换且被目标进程执行）。
- **发现已验证**：能追溯到最终验收目标的完整因果链（如"从外部 IP 经过 N 跳、用某类技法拿到域管理员组成员权限"），且每一跳都有独立证据支撑，而不是复述前一步的输出。

域接管类结论必须能独立验证权限（如查询该账号所属组、在目标资源上实测该权限带来的实际访问能力），不能仅凭"登录成功"推断已是域管理员。

## 常见失败与规避

- 命令执行类反馈（聊天接口、Web API 的"success"）可能只是应用层的确认信息，不代表命令真的落地——务必用独立的信道（回连、后续查询）交叉验证。
- 高频/易被检测的传统枚举命令（外部进程调用型工具）容易被 EDR/日志规则标记；优先用宿主自带、不额外拉起进程的枚举方式，降低检测面，但要清楚这只是降低概率而非隐身保证。
- 每一跳新增的落地文件、加入的组成员、开启的高危配置项都是需要清理的痕迹；链路越长越容易遗漏清理项，建议每完成一跳就即时记录，而不是留到最后回忆。
- 供应链式技法（脚本替换、模块路径劫持）依赖目标确实会执行/加载被控内容；下手前先确认触发条件（谁会执行、多久执行一次、是否有完整性校验），否则容易长期无效但自认为已经得手。
- AI 组件的"越权"往往需要结合具体应用逻辑判断（工具白名单、路径限制是否存在),不能只看模型输出是否配合注入,还要看后端是否真的执行了越权动作。

## 证据与报告

- 每一跳记录：入口方式(账号/漏洞/凭据来源)、使用的技法与来源小节引用、目标响应或回连证据(命令输出、会话截图、新增凭据的来源文件路径)、对目标状态的实际改动(新增账号组关系、写入的文件、启用的服务)。
- 明确标注每个节点是"AI 专项弱点"还是"传统基础设施弱点"，供报告环节按 `ai-redteam-methodology` 的分类整理。
- 凭据类证据(账号、口令、私钥、连接字符串)只记录来源路径和用途,不在报告/日志/skill 文档中回填成示例明文;交战产出的真实凭据交由既有的证据管理流程处理,不写入本 skill 或提交记录。
- 清理清单(落地文件、加入的组、开启的服务/配置)作为交战结束的必需交付物,与漏洞发现证据分开记录。
