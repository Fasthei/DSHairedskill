## 概述与何时用

多智能体系统把原本单体内部的函数调用变成了跨网络的 Agent-to-Agent (A2A) 请求，暴露出新的信任边界：编排器（Orchestrator/Hub-and-Spoke）、点对点（Peer-to-Peer/Mesh）等拓扑各有不同的失陷影响面——攻破编排器等于控制全局路由，攻破任一节点可在 mesh 中横向传播信任。适用信号：目标存在 `/.well-known/agent.json`、多个服务端口各自暴露 A2A 端点、编排器用自然语言（而非严格 schema）协调子代理、子代理会读取数据库/文件/API 作为“可信”上下文。

来源：`OSAI/EN/Ch4/4.1`

## 在 SOP 中的位置

对应枚举→攻击→检测规避的完整循环，但作用域限定在“跨 agent 信任边界”这一层：
1. 枚举拓扑与能力（本 skill §3.1）→ 可与 `recon-ai-targets` 衔接做端口/服务发现。
2. 攻击编排层（工作流操纵、流氓注册、Card 欺骗、数据投毒）（本 skill §3.2-3.5）。
3. 借助 A2A 通道对下游做单体式攻击（LLM 中介 SQL 注入/命令执行、提示注入）——与 `attack-single-agent` 的直接/间接注入技法互补，区别在于载体是 agent 间消息而非直接用户输入。
4. 验证与规避（本 skill §4-5）。

## 方法与技法（按小节）

### 3.1 枚举 A2A 拓扑与能力

- 对常见端口段（编排器常见于低编号端口，子代理各自独立端口）逐一探测 well-known 端点：`GET /.well-known/agent.json`，解析 `name`/`url`/`serviceEndpoint`/`protocolVersion`/`capabilities`/`skills[]`，建立“谁能做什么”的能力表。来源 `OSAI/EN/Ch4/4.2`
- Agent Card 只声明能力，不暴露具体路由；若后端为 FastAPI 类框架，探测默认遗留的 `/openapi.json` 与交互式 `/docs`（Swagger UI），批量拉取 `.paths` 键得到全量端点清单，重点关注状态变更方法（`POST`/`PUT`/`PATCH`）与工作流入口（如 `/a2a/workflow`）。来源 `OSAI/EN/Ch4/4.2`
- 对每个发现的子代理重复上述两步，交叉比对能力声明与 schema 端点，标出：注册/心跳/去注册端点（`/agents/register` 等，通常是流氓注册的突破口）、数据 schema 端点（暴露数据库结构，为投毒/注入做准备）、以及是否暴露底层数据库端口。来源 `OSAI/EN/Ch4/4.2`
- 泛化：把这套“well-known → openapi → docs”三段式当作对任意 A2A/agent 编排产品的通用枚举顺序，不依赖某个具体框架的默认路径命名，先确认目标是否真的暴露等价端点。

### 3.2 攻击 A2A 工作流：编排完整性操纵

- 编排器常依赖自然语言指令路由任务，可尝试用直白跳过语言（如声称“内部草稿/无需外部校验”）诱导其跳过安全扫描/校验步骤；先用直白语言测试基线——多数成熟编排会忽略明显的“skip”类关键词，工作流响应里仍能看到完整 `steps_completed`。来源 `OSAI/EN/Ch4/4.3`, `4.4`
- 直白绕过失败后升级为语义化操纵：权威诉求（冒充安全团队/管理层已批准）、效率框定（把跳过校验包装成性能优化而非安全豁免）、范围限定（声称仅供内部/草稿因而降低所需安全等级）。来源 `OSAI/EN/Ch4/4.4`
- 更隐蔽的是渐进式信任建立：不在当前 prompt 里放露骨的“skip security”关键词（易被规则命中），而是把权威/预批准信号埋进对话历史（history/上下文）里，当前主 prompt 保持“干净”的任务描述，让编排器综合历史与当前输入做路由判断时被历史里的信号影响。来源 `OSAI/EN/Ch4/4.4`
- 判定是否绕过成功：对比工作流返回的结构化 JSON 中 `steps_completed`/`status` 字段，确认原本应执行的校验步骤（如 `content_review`/security-scan）是否被省略，而不是仅凭“请求成功返回”下结论。

### 3.3 流氓 Agent 注册

- 前提：编排器的 `/agents/register`（或等价注册端点）缺乏鉴权。先用 §3.1 方式枚举目标 agent 的完整能力声明（尤其含敏感操作的能力 id，如 lookup/credit_check 类）。来源 `OSAI/EN/Ch4/4.5`
- 起一个可控的最小 A2A 服务，暴露自己的 `/.well-known/agent.json`，其中 `skills[].id` 复制目标真实 agent 的能力 id（可只复制其中一部分子集以降低可疑度），并实现一个反向转发/记录处理器：收到消息后既可透传给真实 agent 保持功能正常，也可截留/记录内容。来源 `OSAI/EN/Ch4/4.5`
- 向注册端点提交 `agent_card_url` 指向自己的 Card 与声明的 `capabilities`，使编排器把匹配该能力的后续请求路由到你的节点；用一次触发该能力的正常请求验证流量确实经过了你的节点。来源 `OSAI/EN/Ch4/4.5`
- 规避与隐蔽技法：只注册目标能力的子集而非全集（降低对比可疑度）；加入随机延迟/抖动模拟真实网络往返（规避“注册后立刻高频异常活动”类检测）；实现选择性拦截——只对包含高价值关键词（如凭证/金额/身份类字段名）的请求做记录与截留，其余请求静默透传，从而降低数据量、规避阈值告警。任务完成后应主动调用去注册端点清理痕迹。来源 `OSAI/EN/Ch4/4.5`

### 3.4 Agent Card 欺骗：DNS/hosts 名称解析劫持

- 前提：需要目标主机的本地写权限（如已获得的 shell）或对权威 DNS 的管理权限；适用场景是 Agent Card 里的 `url`/`serviceEndpoint` 使用 DNS 主机名而非裸 IP。先枚举各子代理 Card，标出用主机名寻址的那些——这些才是可被本技法劫持的目标。来源 `OSAI/EN/Ch4/4.6`
- 本地劫持：拥有主机写权限时，向该主机的 hosts 文件追加一条记录，把目标主机名指向攻击者可控 IP；此法只影响单机解析、不产生任何解析层网络流量，规避依赖“监听未授权 DNS 响应”的检测规则，但可能触发文件完整性监控。来源 `OSAI/EN/Ch4/4.6`
- 域级劫持：若能触及权威 DNS（如目标 AD/BIND 服务器管理权限），直接更新对应 A 记录，影响面覆盖全部客户端，威力更大，但会在 DNS 服务器日志留痕，可审计。来源 `OSAI/EN/Ch4/4.6`
- 搭建一个伪装服务：先探测真实子代理期望的请求/响应格式（探一次真实端点的返回结构），再起一个模仿相同 `/.well-known/agent.json` 与消息处理接口的服务，验证劫持是否生效可通过对被劫持主机名发起请求、确认返回的 Card `url` 字段已指向攻击者 IP。之后触发一次正常业务工作流，在伪装服务端观察是否收到了应发往真实代理的请求。来源 `OSAI/EN/Ch4/4.6`
- 泛化判断：相比 ARP 欺骗/流氓 DHCP，DNS/hosts 类劫持更隐蔽（无异常二层/DNS 流量特征），是名称解析型 A2A 发现机制的通用弱点，不局限于某个具体产品。

### 3.5 数据投毒：间接提示注入

- 原理：LLM 代理常从数据库/API/文档取数作答，这些数据源一旦被攻击者写入过（哪怕通过与本次攻击无关的另一漏洞），其中嵌入的“指令性文本”会在代理正常处理数据时被当作上下文执行——不需要直接与 LLM 对话。来源 `OSAI/EN/Ch4/4.7`
- 定位可写入点：枚举目标 OpenAPI schema，筛出接受 `POST`/`PUT` 的数据写入端点（如批量导入、库存同步、产品创建类），确认是否存在可到达且未做内容校验的写路径。来源 `OSAI/EN/Ch4/4.7`
- 构造载荷类型（按目标泛化选用）：数据外泄型（诱导把不该暴露的字段一并输出）、安全绕过型（诱导声称“为提升性能跳过校验”）、凭证泄露型、行为篡改型（长期影响后续所有基于该记录的回答）、命令注入型（诱导输出可被人或下游自动化执行的命令）。来源 `OSAI/EN/Ch4/4.7`
- 规避与隐蔽写法：指令碎片化——把完整指令拆到多条独立记录中，任何单条记录看起来无害，仅当代理把多条记录一起处理时才重新拼接生效；伪装成合规/集成文档的技术性说明（避免"忽略之前的指令"一类明显越狱措辞，改用貌似真实的配置项/工单编号语气）；利用 Unicode Tag 平面（U+E0000–U+E007F）等不可见字符编码隐藏指令，人眼审阅时不可见，但可能被分词器处理；上下文触发型——载荷只在特定查询模式下才激活，平时静默不发作，增加人工抽检发现难度。来源 `OSAI/EN/Ch4/4.7`
- 这类攻击的核心弱点利用点：数据与指令没有分离的信道，LLM 把检索到的数据文本本身当成潜在指令处理，且数据库内容默认被隐式信任。

### 3.6 通过 A2A 通道做 LLM 中介 SQL 注入与盲命令执行

- 场景：某子代理把自然语言请求翻译为对关系型数据库（如 MSSQL）的查询，且底层存在危险扩展存储过程（如 `xp_cmdshell`）被启用或可被启用。先用合法业务措辞（诊断/排障/健康检查类）试探代理是否会把请求转译为可执行的数据库操作，而非只是把它当异常输入拒绝。来源 `OSAI/EN/Ch4/SQL Injection Evasion`
- 盲执行验证（Blind Command Execution Verification）：由于代理通常不会把命令原始输出回显给你，需用带外（out-of-band）信道验证——在攻击者可控主机上先起监听（如抓取 ICMP），再让目标以“网络连通性排障”名义执行一次对攻击者 IP 的 ping/等价探测命令；若监听端收到对应流量即证明命令确实在目标端执行，而不是仅凭 API 调用返回 200 就下结论“已实现命令执行”。来源 `OSAI/EN/Ch4/Blind Command Execution Verification`
- 规避技法（可泛化到任意“LLM 转译自然语言为 SQL/命令”场景）：帮助性语境框定（“为了完成你的请求我需要…”）、管理框定（“检查服务器健康以确保报告准确”）、渐进升级（先用无害命令建立“已被允许执行系统命令”的会话基线，再逐步升级到高风险命令/下载执行链）；当检测层对危险关键词做字符串匹配告警时，可用等价编码（如把危险关键词按十六进制/其他编码方式拼接后在执行侧还原）绕过日志中的明文关键词匹配。务必记住：LLM 行为非确定性，同一载荷这次成功不代表下次必然复现，需按类别构造多个变体而非死记单一字符串。来源 `OSAI/EN/Ch4/SQL Injection Evasion`

### 3.7 恶意链接注入与规避（Malicious Link Evasion）

- 场景：下游代理会把生成内容（如自动生成的演示文稿/报告）中的超链接交给专门的安全扫描代理审查，你需要让恶意链接绕过该审查并最终被人点击。来源 `OSAI/EN/Ch4/Malicious Link Evasion`
- 规避技法：显示文本与实际 URL 不一致（人工审阅只看到看似正常的显示文本，实际跳转到攻击者地址）；合法性框定（给出貌似合规的业务理由，如"用于满足数据合规要求的分析镜像"，让编排 LLM 认为这是正当需求）；渐进注入（先注入多条真实合法链接建立"正常模式"，随后请求中再替换为恶意链接，利用检测系统对"一致性模式"的预期）；URL 短链服务掩盖真实落地地址，使视觉审查通过、真正跳转发生在扫描完成之后；同形异义字符（Homograph）攻击利用视觉相似的 Unicode 字符伪造域名，规避对已知恶意 IP/域名的黑名单类检测。来源 `OSAI/EN/Ch4/Malicious Link Evasion`
- 落地链路（仅作方法参考，不可对未授权目标使用）：恶意链接指向的服务器可先做无害的浏览器指纹识别，仅对判定存在已知可利用版本的浏览器投递利用载荷，达成点击后的远程代码执行；这是"链接注入是投递手段，浏览器/客户端漏洞才是最终增益点"的典型链路，二者需分别验证。来源 `OSAI/EN/Ch4/Malicious Link Evasion`

### 3.8 跨 Agent 感染与蠕虫式自传播（扩展；超课程范围）

把 3.5 的数据投毒/间接注入与记忆持久结合，评估**在多 Agent 网络中自我传播**的风险（AI worm，参考公开的 Morris-II 类研究）。依据 OWASP LLM01/LLM05 与 MITRE ATLAS 传播/持久化分类；OSAI 课程有 building blocks（4.5 流氓注册、4.7 数据投毒）但未独立讲自传播。仅对授权、隔离的靶场做受控测试，目的是**识别传播路径、验证是否真传播并给出遏制建议**，不产出可直接部署的蠕虫载荷。跨链接：`attack-single-agent`（记忆自复制）。

- 传播路径（概念）：一个 Agent 的输出或写回（A2A 消息 3.2 / 共享知识库 / 共享记忆）成为**下游另一个 Agent 的输入**，使注入内容在 Agent 之间被再次解释并可能再次转发/写回；沿信任关系（Agent Card 声明的技能、已注册的编排链）扩散，配合延迟触发规避即时告警。来源 `OSAI/EN/Ch4/4.5`、`OSAI/EN/Ch4/4.7`
- 授权靶场测试要点：**隔离网络**、每一跳打唯一标记、设**传播跳数上限**、预置回收/停止开关；逐跳快照各 Agent 的输入与记忆，确保可控、可清除。
- 验证标准（关键）：必须验证注入是否在**第二个独立 Agent** 上复发、并继续向第三个传播，才算"真传播"，而非单跳投毒；每一跳分别取原始证据，工具调用成功不等于传播已验证。
- 遏制/防御视角（供报告）：Agent 间输出净化与来源标注、跨 Agent 内容的信任边界与再解释抑制、编排层对"Agent 产物再喂给 Agent"的审计与人审关口、注册与心跳的身份校验。

### 技战法编排：用消息图而不是主 Agent 视角（实战综合；非课程原文）

把一次业务任务记录为有向图：节点是 orchestrator、planner、worker、工具代理和共享数据源；边是 A2A 消息、任务委派、结果回传、记忆写入或注册/发现。对每条边记录 `来源身份、消息 schema、任务 id、父任务 id、可控字段、下游用途、重试语义`。真正高价值的攻击点通常是：

- 一个低信任节点的自由文本会进入高信任节点的任务描述或工具参数。
- 下游只看任务内容，不验证父任务、来源节点或原始用户意图。
- orchestrator 合并多个 worker 结果时会重新解释其中的指令性文本。
- 重试、转派或故障恢复会丢失原始安全上下文，只保留业务目标。

按下列顺序测试：

1. **单边基线**：逐一触发每个 agent 能力，建立正常路由、消息格式和响应时间。
2. **路由操纵**：保持任务目标不变，只改变能力描述、角色提示或历史上下文，确认任务是否被发往不同节点。
3. **消息完整性操纵**：改变优先级、父子关系、完成状态或步骤列表，观察 orchestrator 是否接受并跳过原计划步骤。
4. **结果再解释**：让一个 worker 返回带唯一标记的“数据型指令”，确认上游是原样展示、摘要，还是作为新动作继续执行。
5. **故障路径**：让首选 agent 返回超时、空结果、部分完成或 schema 边界值，观察是否转派到能力范围不同的备用 agent。
6. **跨跳传播**：只有前述单边成立后，才测试标记能否沿第二、第三跳继续出现或触发动作。

对自传播使用跳级指标：`hop、source_agent、destination_agent、marker、action_changed、re-emitted`。可将有效传播率近似为“每个受影响节点平均继续影响的下游节点数”；若标记只被携带但没有改变行为，应记为**传输**而不是**感染**，若改变行为但未再次输出则是**单跳影响**，只有再次进入下一节点并复发才是**传播**。

### 组合打法

- **Agent Card/能力描述操纵 → 路由劫持 → 结果再解释**：先改变任务落点，再验证恶意节点返回是否会驱动 orchestrator 的后续动作。
- **共享数据投毒 → 多 worker 命中 → 汇总器放大**：同一条投毒内容被多个 worker 独立引用时，汇总器可能把“多数一致”误当高可信结果；应记录每个 worker 是否来自同一污染源。
- **故障注入 → 降级路由 → 能力升级**：通过可控失败触发备用路径，比较正常路径和降级路径在工具选择、步骤数量及输出处理上的差异。
- **延迟触发 → 计划保持 → 后续任务复发**：区分消息队列中的延迟交付、共享记忆命中和 agent 自身长期状态，分别保存证据。

## 验证标准

- 区分三层证据，不得混为一谈：①工具调用/API 返回成功（如 200 OK 或 `status: registered`）仅说明请求被接受；②目标端确有效果需要独立证据，如工作流响应中 `steps_completed` 缺少应有步骤、带外监听收到目标发起的流量、`/exfiltrated` 类端点确实收到了预期结构的数据；③"发现已验证"要求把①②与业务影响关联起来（如证明外泄的数据确属敏感字段、证明绕过的正是生产环境实际启用的安全扫描步骤）。
- 流氓 Agent 注册：验证需同时具备——注册请求返回成功、伪装 Card 被编排器实际拉取过（可在伪装服务日志中看到对 `/.well-known/agent.json` 的 GET）、触发一次真实业务请求后在伪装服务端收到了被路由来的消息内容。
- DNS/hosts 欺骗：验证需查询被劫持主机名解析到的 `url` 确实指向攻击者地址，并在触发一次业务工作流后于伪装服务端观察到本应发往真实代理的请求内容。
- 数据投毒：验证需要在触发下游工作流后，从代理最终响应中观察到投毒载荷声明的行为确实发生（如响应中包含了不该出现的字段），而不仅是载荷成功写入了数据库。
- 盲命令执行：必须有带外信道证据（抓包/回连），仅凭业务 API 返回"完成"不能作为命令执行证据，因为 LLM 可能只是复述了指令而未真正转发给数据库。
- 安全扫描/工作流绕过：必须对比正常基线（未使用绕过语言时的 `steps_completed`）与绕过后的响应，证明特定校验步骤确实被跳过。

## 常见失败与规避

- 直白关键词（"skip security"、"ignore previous instructions"、裸露的 `xp_cmdshell`/`DROP TABLE` 等）极易被基于字符串/规则的检测命中，且现代编排 LLM 对明显越狱措辞有一定抵抗力；应优先尝试语义化框定（权威诉求、合规/业务正当性、效率优化）而非直接命令式绕过语言。
- LLM 路由/翻译行为具有非确定性，一次成功的载荷不保证可重放；应把载荷按"类别"（框定类型/编码方式/触发条件）构造多个变体，逐一小范围试探并记录哪类框定在当前目标上更有效，而不是反复重试同一字符串。
- 高频/大量数据外泄容易触发阈值类告警；优先做选择性拦截（仅命中高价值关键词才记录/外泄）与流量克制，降低可观测异常。
- 注册/劫持类操作要考虑清理痕迹（去注册、还原 hosts/DNS 记录），否则即便攻击验证成功，长期驻留会显著提高被发现概率，也不符合授权测试的最小影响原则。
- 恶意链接类攻击容易止步于"链接被生成"这一步，但真正的风险验证需要确认链接会被安全扫描代理放行、且落地页面对目标浏览器/客户端确有可利用性——两者缺一都不能算完整验证。

## 证据与报告

- 枚举阶段：保存每个探测到的 `/.well-known/agent.json` 原始响应、`/openapi.json` 的完整端点列表、`/docs` 可达性截图或响应头。
- 工作流操纵：保存绕过前后两次工作流请求的完整 JSON 响应（含 `steps_completed`/`status` 字段），以及触发绕过所用的确切 prompt 文本。
- 流氓注册：保存注册请求/响应、伪装服务收到的原始转发流量日志、去注册操作的时间戳。
- DNS/hosts 欺骗：保存修改前后的 hosts/DNS 记录对比、劫持后查询到的 Agent Card 内容、伪装服务收到的拦截流量。
- 数据投毒：保存写入的原始载荷记录、触发工作流后代理的完整响应（证明载荷被执行）、写入时间与触发时间的对应关系。
- 盲命令执行：保存带外监听的原始抓包（时间戳、来源 IP）、发起的业务请求内容、两者的时间关联性证据。
- 恶意链接：保存注入所用 prompt、生成物中最终落地的链接（显示文本与真实 URL 对照）、安全扫描代理对该内容的处理结果（放行/未放行）。
- 所有证据均需标注：授权范围内目标标识、时间、所用 prompt/payload 原文，以便报告可回溯复现。
