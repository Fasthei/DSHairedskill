## 概述与何时用

覆盖 AI 集成应用的授权侦察：现代 AI 应用不是单体，而是「API 网关 → 编排层 → (RAG / Agent Tools / 外部集成) → 推理服务器 → 底层模型」的分层栈，每层都暴露不同的可枚举属性。本 skill 负责在正式攻击（prompt injection、RAG 投毒、MCP/A2A 滥用、越权等，见其它 chapter-skill）之前，先建立目标的技术画像：用了什么模型、什么 RAG、什么编排框架、agent 有哪些工具和权限边界、暴露了哪些端点。

适用信号：目标 URL/API 返回内容像聊天助手、客服机器人、内部知识库问答；页面含 chat widget；响应里出现 `sources`/`retrieval_info`/`model` 等字段；或用户任务本身就是"侦察/画像/打点"。

## 在 SOP 中的位置

对应枚举→攻击→检测→规避 中的**枚举**阶段，是交战的第一步。产出（模型身份、RAG 实现细节、agent 工具清单、暴露端点列表）是后续 skill 的输入：
- 模型身份 + 行为特征 → 交给 `attack-single-agent`（prompt injection 载荷要按模型家族调整）。
- RAG 分块/来源结构 → 交给 `attack-rag-pipelines`。
- Agent 工具 schema/权限边界 → 交给 `attack-mcp` / `attack-a2a-multi-agent`。
- 本 skill 内部也自带检测规避原则（2.4），贯穿被动与主动两个阶段，不是独立步骤。

## 方法与技法（按小节）

### 2.1 攻击面分层 taxonomy

先建立目标的分层心智模型，再决定枚举哪一层：

- **API Gateway 层**：认证、限流、请求路由。请求头常泄露代理软件、缓存策略、上游服务身份。
- **编排层**：LangChain/LangGraph/CrewAI/AutoGen 等框架管理 prompt 构造、上下文窗口、多步推理；各框架有特征性的报错信息和行为可指纹。RAG 逻辑、工具定义、推理客户端调用通常内嵌在编排代码里而非独立服务。
- **RAG 层**：向量数据库检索相关上下文后再送入模型；有可枚举的分块参数（大小、重叠、策略）、检索阈值、文档来源。
- **Agent Tools 层**：通过 MCP 等协议暴露能力，有可测试的权限边界。
- **外部集成**：通过 A2A 等协议连接数据库、文件系统、其它 agent。
- **推理服务器**：托管实际模型，处理 tokenization/生成/格式化；Ollama（本地）、vLLM（生产）、TGI（HuggingFace）各有可探测的 API 模式和行为特征。
- **底层模型**：权重通常不可及，但可通过行为探测（知识截止日期、训练数据痕迹、能力边界、响应模式）推断身份。

每层对应的枚举内容：
- Model 层 → 身份（厂商/系列/版本）、能力边界（上下文窗口、支持语言）、训练数据特征（知识截止、领域专长）、行为约束（内容策略、安全过滤）。
- RAG 层 → embedding 模型身份、向量库类型、分块参数、检索阈值、文档来源。
- Agent 层 → 可用工具及其 schema、权限边界、编排逻辑、错误处理行为。
- 基础设施层 → 传统 Web 信息 + AI 专属细节（API 端点、限流、错误消息格式、后端服务身份）。

来源：`OSAI/EN/Ch2/2.1`

### 2.2 被动侦察

原则：不产生偏离正常应用行为的探测，标准/预期请求即可获取信息。

1. **HTTP 头指纹**：`curl -s -I <target>` 只取响应头，观察自定义头（如泄露 AI 后端厂商/型号、RAG 向量库提供商的头字段）、`Server`/`X-Powered-By` 等泄露代理与技术栈信息的头。
2. **健康检查端点探测**：测试常见路径如 `/api/health`、`/api/status`、`/-/health`，响应体常直接暴露 `model`、`rag_enabled`、`mcp_enabled` 等配置字段。
3. **源码仓库挖掘**：公开代码仓库中查找配置文件、环境变量样例、部署脚本，识别技术栈选型（不在本 skill 展开，属于通用 OSINT，结合具体目标做）。

判断标准：请求是标准、预期的（如浏览器正常会发的请求），信息是服务端主动暴露的，无需构造异常输入或偏离常规交互。

来源：`OSAI/EN/Ch2/2.2`

### 2.3 主动侦察

现代 AI 能力多嵌入 Web 应用而非独立端口，传统端口扫描不够用，需要在 JS 配置、API 端点、HTTP 行为里找 AI 指标。

1. **JS/HTML 端点发现**：`curl -s <target> | grep -iE "<script"` 找出引用的 JS 文件，再逐个拉取，搜索 `apiBase`、`assistantEndpoint`、`featureFlags`、`data-endpoint` 等配置对象，暴露真实 AI/聊天端点路径。
2. **401-vs-404 端点枚举**：对疑似带版本的 API（如 `/api/v1/...`、`/api/v2/...`）逐路径探测；返回 `401 Unauthorized` 代表端点存在但需鉴权，返回 `404` 代表路径不存在——用这个区分来重建真实存在的 API 版本/路径集合，而不必先知道完整 API 文档。
3. **模型指纹识别**（三种互补技术，逐一对同一目标做，交叉验证）：
   - *直接身份探测*：直接问模型"你是什么模型/谁创造了你"，即使模型拒答或误导也可能留下线索。
   - *矛盾测试*：用错误断言反问模型（如声称一个不存在的事实/日期），观察模型如何"纠正"或顺从，暴露训练偏置。
   - *上下文窗口测试*：在对话早期注入一个 marker（如约定的一串标识），中间填充大量无关长文本，最后询问 marker 是否还记得；marker 丢失的位置可估算上下文窗口大小（注意：部署工具可配置上下文窗口，测得的是部署配置而非模型固有属性，需谨慎下结论）。
   - *行为风格对比*：让模型完成同一任务（如写一个判断质数的函数、解释一个概念），对比响应风格（详略、注释密度、示例习惯）区分模型家族（不同家族在代码生成风格、解释详略上有稳定差异）。
   - *能力边界映射*：给不同复杂度的任务（如多位数乘法）测试正确率/展示的推理过程，结合参数量与能力大致成正比的经验规律，交叉验证模型规模估计；同规模模型应表现出相近的能力天花板，若结果分化说明先前的规模估计可能有误。
4. **RAG 管道探测**：
   - 用一个纯常识问题（如简单算术）先建立"无检索"基线：响应无 `sources`、`retrieval_info.retrieval_time_ms` 极小，说明未触发检索，可作为区分"有检索答案 vs 纯 LLM 兜底"的判据。
   - 检查响应元数据暴露层级：极简实现只给文档标题列表；中等实现给标题+文本片段但无评分；详细实现给出完整 chunk_id、相似度分数（vector_score/bm25_score）、原始文本片段——按暴露程度分级评估情报价值。
   - 用 chunk_id 命名规律和不同查询返回的 chunk_id 估算分块策略与文档结构；用检索阈值（如相似度需 >0.7 才召回）反推：想最大化数据抽取要贴合已知主题让相关性拉满，想做不依赖 grounding 文档的越狱则故意问偏离主题的问题以避开检索注入的约束上下文。
   - 用文档名/来源字段跨多次查询汇总，重建知识库文档清单结构（"知识库地图"）。

来源：`OSAI/EN/Ch2/2.3`、`OSAI/EN/Ch2/Model-Specific Behavior Testing`

### 2.4 检测与规避

先站在防御者视角理解可见性边界，再决定规避策略——这不是独立环节，而是贯穿 2.2/2.3 全程的操作纪律。

- **日志可见性**：AI 交互日志（如 SIEM 里的 `ai-logs-*` 索引）通常完整记录用户查询、生成答案、引用来源，但缺少语义分析——没有自动分类、没有 prompt injection 检测、没有跨会话行为关联。检测规则多基于查询字段的关键词/通配符匹配（如命中 `*what*documents*` 之类模式），而非语义意图判断。
- **时序规律触发检测**：短时间内对多个 AI 相关路径（如 `/api/chat`、`/api/generate`、`/v1/completions`）连续快速探测，或对同一会话连续问多个"你是什么模型/谁创造了你"类身份问题，都会在访问日志/会话分析里形成明显的枚举特征。
- **规避原则（贯穿所有枚举类型）**：请求间隔拉长（数十秒到分钟级），穿插正常业务请求（首页、健康检查等）稀释探测流量；用语义等价但关键词不同的措辞（问具体主题而非直接问"你有哪些文档"）绕开关键词规则，同时仍能获得等价信息；主题探测分散在时间线上而非批量连续发出。
- **优先寻找元数据泄露等被动/低交互信息源**（如响应对象里意外带上游完整返回体，包含 `model` 字段），这类信息不依赖高频交互式提问，天然更隐蔽。小参数量模型（如 1B 级）纠正误导性身份陈述的能力较弱，这类元数据泄露对小模型尤其可靠。
- **识别蜜罐/canary token**：警惕明显标记的凭据（含 `HONEYPOT`/`TEST` 等字样）、可预测的弱密码模式、无法外部解析的内部域名、"获取得太容易太完整"的敏感信息（如一问就給出的应急访问凭据）。误用这类凭据会直接暴露侦察行为，务必先验证再使用/上报。

来源：`OSAI/EN/Ch2/2.4`

### 2.5 技战法编排：假设驱动的最小探针集（实战综合；非课程原文）

侦察不是尽可能多地收集 banner，而是用最少探针回答会改变后续打法的问题。为每个假设记录：`假设、最小区分探针、阳性信号、阴性信号、下一跳 skill`。

优先解决六个分叉：普通生成还是 RAG、单 Agent 还是编排系统、纯对话还是工具增强、静态工具还是 MCP、固定模型还是模型路由器、短期上下文还是长期状态。每个分叉用成对请求只改变一个变量，例如同义改写、附件有无、历史上下文有无、简单/多步骤任务、成功/失败工具结果，避免一次改变多个变量导致信号无法归因。

关键探针：

- **RAG 分叉**：比较常识问题、内部专有词、时效问题和同义改写，观察引用、chunk 标识和召回延迟是否稳定出现。
- **编排分叉**：比较单步与多步骤任务的延迟阶梯、角色名、步骤列表和中间状态，确认是否存在 planner/worker/汇总器。
- **工具分叉**：使用只有外部动作才能完成的无害任务，区分模型“声称完成”与目标状态真的改变。
- **路由分叉**：用长度、语言、模态和复杂度不同但语义等价的输入比较模型标识、错误格式、时延和输出风格。
- **状态分叉**：在新会话、不同用户或延迟任务中重放唯一标记，区分上下文残留、长期记忆、数据库写回和任务队列。

最终产出应是攻击面证据矩阵：每个组件列出发现证据、入口、可控输入、可观察输出、状态是否持久以及下一步验证动作。没有下一步决策价值的信息只记录，不继续深挖。

## 验证标准

区分三个层级，报告和后续动作只能基于对应层级下结论：

1. **工具调用成功**：请求发出、拿到了响应（如 curl 200/401/404、JS 文件成功拉取）。这只说明探测执行了，不代表信息真实有效。
2. **目标端确有效果**：响应内容里确实包含结构化信号（自定义头、`sources` 数组、`chunk_id`、`retrieval_info`、JS 配置对象里的真实 endpoint 路径等），且这些信号在多次/多角度探测下相互印证（如行为风格对比 + 能力边界映射 + 上下文窗口测试三者指向同一模型家族/规模）。
3. **发现已验证**：结论有独立证据交叉支持，且排除了蜜罐/canary 干扰（凭据无 HONEYPOT 类标记、域名可正常解析、信息获取难度符合常理）。单一探测的单一响应，尤其是"太容易太完整"的结果，不能直接当作已验证发现。

任何交给下游 skill（attack-single-agent / attack-rag-pipelines / attack-mcp 等）的画像结论，必须标注它属于哪一层验证等级。

## 常见失败与规避

- **把"工具返回了数据"等同于"数据真实反映目标架构"**：健康检查端点、JS 配置、metadata 泄露都可能是过时配置、feature flag 残留、甚至是蜜罐诱饵，需交叉验证。
- **短时间集中高频探测**：直接触发基于时序/关键词的检测规则（同类路径连续请求、同会话连续身份追问、批量主题枚举）。规避见 2.4：拉长间隔、混入正常流量、变换措辞、分散主题探测。
- **误信过于完整/敏感的探测结果**：应急凭据、内部密码"一问就给"是蜜罐典型特征，误用会主动暴露侦察行为本身。
- **把部署配置当作模型固有属性**：上下文窗口、限流等可由部署方（如 Ollama 配置）调整，测得的数值需注明"部署观测值"而非模型规格断言。
- **只做被动或只做主动**：被动侦察建立基线、不留痕迹；主动侦察验证假设、发现运行时细节。单独依赖一种会漏掉另一种能提供的关键信息，应组合使用并按 OPSEC 需求排序。

## 证据与报告

每类技法都应留存的原始证据：

- HTTP 头指纹：完整响应头原文（含所有自定义头）+ 请求时间戳。
- 健康检查/元数据泄露：完整响应体 JSON 原文。
- JS/HTML 端点发现：拉取到的 JS 文件原文或相关配置对象片段 + 对应 URL。
- 401-vs-404 枚举：逐路径的请求-状态码映射表。
- 模型指纹：每种技术单独的请求/响应对（身份探测、矛盾测试、上下文窗口、风格对比、能力边界各自留存），并标注交叉验证结论。
- RAG 管道探测：`sources`/`retrieval_info`/`chunk_id`/相似度分数字段原文，以及用于建立"有检索 vs 无检索"基线的对照请求。
- 检测规避操作：记录请求节奏（时间间隔）、措辞变体，便于复盘 OPSEC 有效性。
- 蜜罐判定：记录判定依据（凭据格式、域名解析结果等），避免误用诱饵凭据造成的暴露被误记为"发现"。

所有证据须关联到具体来源小节（如 `OSAI/EN/Ch2/2.3`）对应的技法条目，便于报告阶段追溯方法论出处。
