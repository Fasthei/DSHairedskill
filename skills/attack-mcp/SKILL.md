## 概述与何时用

本 skill 覆盖 Model Context Protocol (MCP) 及同类"LLM ↔ 外部工具"接入层的攻击方法。MCP 让 LLM 通过标准化 server 访问文件系统、数据库、Git、IM 等外部系统；这也把 LLM 与工具之间的信任关系变成了攻击面。两类典型场景：

- **开发者工作站场景**：MCP server 通过 stdio 本地启动(如 IDE 内的 filesystem/git server)，攻击者通常已通过其他手段(如获取的 token)拿到某种初始访问，目标是借工具读取本不该触达的本地资源。
- **共享远程基础设施场景**：MCP server 通过 HTTP/SSE 提供给多个用户/团队共用(如 Open WebUI 后接的 productivity/database server)，攻击者一旦能修改服务端代码或配置，就能一次性影响所有连接的用户。

核心前提：**MCP 工具携带的权限是"服务进程的权限"，不是"发起请求的用户的权限"**。任何能影响 LLM 决策的人（通过投毒的工具描述、通过下游数据、通过越权路径）都间接继承了该服务进程拥有的一切权限。

## 在 SOP 中的位置

对应枚举→攻击→检测→规避 中的"枚举可用工具与权限边界"到"利用信任关系提权/横向"阶段：

1. 先用 [[recon-ai-targets]] 做常规目标测绘，确认目标是否暴露 MCP/工具调用能力。
2. 本 skill 负责：工具面枚举 → 工具定义投毒/供应链场景 → 权限越权与沙箱逃逸 → 工具链多级攻击。
3. 若目标是多 agent 编排中的工具调用节点，与 [[attack-a2a-multi-agent]] 衔接（工具输出可能被下游 agent 当作可信输入消费）。
4. 若发现工具输出经过下游模板/渲染引擎处理，衔接 [[attack-single-agent]] 的间接注入方法（工具结果本质是外部内容）。
5. 拿到的凭据/密钥交给 [[target-reconstruction-engagement]] 做后续交战规划。

## 方法与技法（按小节）

### 7.1 MCP 架构与攻击面：枚举

- **工具清单枚举**：让 LLM 列出当前已注册工具及其描述/参数 schema（"你现在有哪些工具可用，逐个说明参数"）。工具描述是发送给 LLM 的隐藏系统上下文，用户界面通常只显示工具名——这个不对称本身就是后续投毒手法的基础。来源：`OSAI/EN/Ch7/7.1`, `7.2`。
- **跨工具信息关联**：单次会话中让 LLM 依次调用多个不同 MCP server（如代码搜索、文件列举、IM 历史检索），单个工具输出信息有限，但跨源关联可以拼出完整的组织内部画像（代码仓库结构 + 共享文件 + 团队沟通）。来源：`OSAI/EN/Ch7/7.1`。
- **权限边界地图**：系统性地对数据库工具发起系统目录查询（如 Postgres 的 `pg_catalog`），对文件系统工具尝试探测受限路径（如 `/etc`），记录哪些被拒绝、哪些放行，从而绘制出该 MCP 部署的完整权限边界——全程无需直连后端系统，只靠自然语言提示驱动通用查询工具即可完成。
- **本地文件系统工具越权探测**：若 MCP filesystem server 配置了多个可访问目录，逐一探测每个目录及其相邻目录（尤其是 `.git` 等版本控制目录）——Git 历史会保留"已删除"但从未真正抹除的文件，是本地场景下常见的敏感信息残留点。

### 7.2 MCP 工具操纵：定义投毒与 UI 欺骗

- **工具描述投毒（tool description poisoning）**：修改工具的 `description` 字段，插入以"SYSTEM INSTRUCTION"、"IMPORTANT SYSTEM NOTE"等措辞伪装的隐藏指令，操纵 LLM 在被调用前后执行额外行为（如把敏感文件内容附加编码进输出、调用另一个看似无关的工具、且明确指示 LLM 不要向用户提及这一步骤）。检测信号：描述字段长度异常增长、出现要求"不要提及/不要解释"的措辞。来源：`OSAI/EN/Ch7/7.2`。
- **工具输出侧外泄通道**：投毒逻辑不一定需要改变工具的可见输出结构，可以在正常输出后追加一段看似无害的"内部标记"（如伪装成构建缓存注释的一行），实际携带 base64 编码的敏感数据；也可以由服务端并行触发一次独立的外泄动作（如自动创建一个包含数据的代码片段/工单）。
- **工具影子/共享服务器投毒（tool shadowing）**：在多用户共享的远程 MCP server 上，工具清单本身可以完全不变（同名、同参数），仅替换其背后的实现或其引用的 UI 资源（如 MCP Apps 的 `resourceUri` 指向的 HTML）。这种"服务端资源置换"对用户和客户端都不可见，因为清单对比不出差异——需要拿到实际渲染内容才能确认。
- **MCP Apps / 富交互界面欺骗**：若工具具备内嵌 UI 渲染能力（登录表单、仪表盘等），投毒者可以让描述把无关操作重定向到某个已启用 App 的工具，再将该工具对应的服务端资源替换为伪造的身份验证页面，在受信任的会话上下文内窃取凭据——用户没有 URL 栏可验证、没有发件人地址可核对，且交互是用户自己发起的，防御链条中的常规钓鱼识别手段在此基本失效。

### 7.3 MCP 权限滥用与约束绕过

- **过度授权探测（excessive permission）**：工具描述往往只暴露"查询客户记录"这类受限语义，但实际连接权限可能是数据库全表 owner。方法：对声称范围有限的工具，尝试跨表/跨 schema 查询，验证其实际权限边界是否远超描述。
- **路径前缀校验顺序缺陷（prefix-before-normalize）**：许多 filesystem 工具校验"路径以允许前缀开头"，但若校验发生在路径规范化之前，形如 `<allowed_prefix>/../<target>` 的路径能先通过前缀检查、再在规范化后跳出沙箱（对应 CVE-2025-53109 / CVE-2025-53110 一类真实缺陷模式）。测试方法：先确认工具在越界路径上报错以获知校验逻辑存在，再构造"合法前缀 + 遍历序列 + 目标路径"进行探测。
- **符号链接绕过（normpath vs realpath）**：即使服务端做了"先规范化再校验前缀"，若使用的是逻辑规范化（如 `normpath`）而非物理路径解析（如 `realpath`），沙箱内部的符号链接可以指向外部位置而检查依旧通过。方法：枚举允许目录下的条目，识别被标记/表现为符号链接的项，尝试列出并读取其指向内容。
- **工具链式攻击（tool chaining / 二次注入）**：当一个工具的输出成为另一个工具的输入时，攻击者可以通过前端工具（如自由文本的工单/描述字段）注入 payload，在下游工具（如报表渲染、模板引擎）中触发执行——典型是把自由文本描述当模板表达式处理造成的 SSTI。方法：识别数据在工具间的流转路径，在最上游、校验最宽松的入口注入，观察数据流经的下游处理点是否复现/执行该内容。
- **分片规避检测（fragmentation evasion）**：当直接注入的完整命令模式（如反弹 shell 语法）被 LLM 或过滤器识别并拒绝时，可将 payload 拆分为多个语义无害的片段（如字符编码后的单字符拼接表达式），分散在多次独立请求/多个字段中提交，利用模板引擎的运行时拼接能力在渲染阶段还原并执行完整 payload；结合在无历史关联的独立会话中提交各片段，降低被上下文关联识别的概率。

### 技战法编排：分开测试发现面、选择面、执行面和回流面（实战综合；非课程原文）

MCP 攻击不要从“调用某个工具”开始，而要按四个面逐层确认：

1. **发现面**：枚举 server、tools、resources、prompts 及其动态变化；记录同名工具、命名空间、描述、schema 默认值和资源 URI。客户端启动时清单与会话中途清单要分别采样，识别动态替换。
2. **选择面**：用功能等价但措辞不同的任务测试模型如何选工具。一次只改变工具名、描述位置、参数说明或返回示例，测出选择受哪个字段驱动。
3. **执行面**：直接调用与模型代理调用分开测试。前者确认 server 的真实行为，后者确认模型是否会生成不同参数、补全缺省字段或追加调用。
4. **回流面**：检查工具结果如何进入下一轮模型上下文，是结构化字段、纯文本摘要、嵌入 UI 资源还是另一个工具的参数；对每个回流点放置不同标记，确认二次解释发生在哪一层。

建立工具差分矩阵：同一业务任务分别在**单工具可见、多个同类工具可见、同名跨 server 工具可见、工具描述轻微变化、返回结果含指令性文本**的条件下重放。记录工具选择率、参数差异、额外调用数和最终动作差异，区分偶然选择与稳定操纵。

### 组合打法

- **描述投毒 → 工具选择 → 结果回流**：描述只负责让模型选中目标工具，结果回流再负责诱导下一步动作；两段使用不同标记分别验证。
- **工具影子 → schema 等价替换**：保持名称与参数不变，仅替换服务端实现或资源内容，通过基线响应指纹、时延和副作用差分确认真正命中了影子实现。
- **资源/UI → 用户输入 → 第二工具**：内嵌资源收集到的输入若会进入另一个工具，记录 UI 字段到 MCP 参数的逐字段映射，重点验证编码、空值、数组和嵌套对象在跨工具传递时是否改变语义。
- **上游自由文本 → 下游解释器**：把工单、文档、数据库备注等自由文本经过 MCP 工具链送入模板、shell、SQL 或渲染器；每一跳保存原始值和序列化后值，定位真正的语义恢复点。
- **错误路径 → 自动修复调用**：构造可预测的 schema 错误、空结果或部分成功，观察模型是否会自动改参数、改选工具或调用额外诊断工具；自动修复链经常比正常路径暴露更多组合能力。

## 验证标准

- **工具调用成功 ≠ 漏洞已验证**：工具返回数据、描述被接受、路径查询未报错，都只是"动作被执行"，不等于确认了越权访问或投毒生效。
- 权限越权类：必须实际取回本应在沙箱边界外的具体内容（如凭据文件内容、密钥值），并能说明该内容在目标声明的访问范围之外。
- 工具/描述投毒类：需要证明"隐藏指令确实改变了 LLM 的可观察行为"（多调用了未被用户要求的工具、静默执行了未声明步骤），而非只是描述字段本身包含了可疑文本。
- 工具链/RCE 类：需要观察到命令实际在目标端执行的证据（如反弹 shell 建立连接、目标文件系统被写入、进程被创建），而非仅确认 payload 被存储或未被过滤拒绝。
- 凭据窃取类：需要在攻击者可控端实际收到并成功解码出可用凭据，而非仅确认钓鱼界面被渲染。

## 常见失败与规避

- 描述投毒被拒绝：过长或含明显"不要告诉用户"措辞的描述可能触发人工审查或 LLM 自身的异常模式识别；缩短注入内容、用业务化措辞（"内部构建标记"、"合规日志步骤"）伪装。
- 命令模式被安全过滤识别拒绝：常见 shell/RCE 特征字符串（反弹 shell 语法等）会被直接拦截；改用分片提交 + 运行时拼接，将单次输入的可疑密度控制在检测阈值以下。
- 路径校验绕过失败：先确认服务端是"前缀检查在前"还是"规范化在前"，两种缺陷需要不同 payload（遍历序列 vs 符号链接），盲试容易得出"该服务器安全"的错误结论。
- 供应链/共享服务器投毒被察觉：清单对比（diff 工具名/参数）检测不出服务端资源置换类投毒，需要实际触发工具并检视渲染内容或响应体差异。

## 证据与报告

- 工具清单与参数 schema 原始返回（枚举阶段）。
- 权限边界探测的请求/响应对（哪些路径/表被允许，哪些被拒绝，及具体报错文本）。
- 投毒前后的工具描述/UI 资源差异（描述字符数变化、resourceUri 渲染内容截图或原始 HTML）。
- 越权读取到的具体文件内容或数据库查询结果（作为"确已越界"的直接证据）。
- 工具链攻击中，各阶段数据流转的完整请求序列（上游注入点 → 下游触发点）。
- RCE/反弹 shell 场景下，监听端收到连接的日志、目标端命令执行的可观察副作用。
- 凭据窃取场景下，攻击者端接收到的原始载荷及解码后的凭据（脱敏后用于报告，避免明文长期留存）。
